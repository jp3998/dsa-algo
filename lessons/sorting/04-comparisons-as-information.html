Comparisons as Information and the Decision Tree Model

"Every comparison is a binary fork in the road. By representing an algorithm as a decision tree, we can prove an unyielding physical law: the height of the tree—and thus the worst-case running time of any comparison algorithm—is bounded below by the logarithm of the permutation space."

4.1 The Binary Branch: At Most One Bit per Query

In Chapter 3, we proved that sorting an array of $n$ elements requires eliminating $n! - 1$ incorrect permutations, resolving an initial uncertainty of: $$H = \log_2(n!) \text{ bits}$$

Now we must examine the mechanism of elimination: the comparison query.

In the comparison model, every query asks: "Is $A[i] < A[j]$?" Assuming distinct keys, this question has only two possible outcomes: Yes or No.

Therefore, any single comparison can split the current set of $K$ remaining suspect permutations into at most two disjoint subsets:

$$S = S_{\text{left}} \cup S_{\text{right}}$$
  • $S_{\text{left}}$: the permutations where $A[i] < A[j]$.
  • $S_{\text{right}}$: the permutations where $A[i] > A[j]$.

When the oracle returns an answer, the algorithm discards one of these two subsets entirely.

The Information Bound of a Comparison

In the most ideal scenario imaginable, the comparison splits the suspect pool perfectly in half: $$|S_{\text{left}}| = |S_{\text{right}}| = \frac{K}{2}$$ In this best-case split, the uncertainty decreases by: $$\log_2(K) - \log_2(K/2) = \log_2(2) = 1.0 \text{ bit}$$

If the split is unbalanced (for example, $90\%$ vs $10\%$), an adversary can force the algorithm into the larger subset, yielding strictly less than $1$ bit of progress.

Therefore, a single pairwise comparison can yield at most $1$ bit of information.

4.2 The Decision Tree Model of Algorithms

Because a deterministic algorithm must choose which comparison to perform next based strictly on the answers to its previous queries, the entire execution of an algorithm on an array of size $n$ can be modeled as a binary tree.

Definition 4.1 (Binary Decision Tree for Sorting)

A decision tree for sorting $n$ elements is a binary tree where:

  • Internal Nodes: Each internal node represents a comparison between two indices, written $A[i] : A[j]$.
  • Branches: Each internal node has two outgoing edges:
    • Left edge: the outcome $A[i] < A[j]$.
    • Right edge: the outcome $A[i] > A[j]$.
  • Leaves: Each leaf node represents a final sorted permutation output $\pi \in S_n$.

How Execution Corresponds to Tree Traversal

When an algorithm runs on a specific input array $A$:

  1. It begins at the root node and performs the root comparison.
  2. Depending on whether the outcome is $<$ or $>$, it follows the corresponding branch down to the next node.
  3. It repeats this process down the tree until it reaches a leaf, where it outputs the final sorted permutation.

The number of comparisons performed on that specific input is exactly the depth of the leaf reached (the number of edges traversed from the root).

Therefore, the worst-case number of comparisons performed by the algorithm is the length of the longest path from the root to any leaf—which is precisely the height $h$ of the decision tree!

4.3 The Leaf Reachability Theorem

How many leaves must a correct decision tree possess?

Theorem 4.1 (Leaf Reachability Bound)

Any decision tree that correctly sorts every possible input sequence of $n$ distinct elements must contain at least $n!$ leaves:

$$L \ge n! \tag{4.1}$$

Proof by Contradiction:

Suppose an algorithm's decision tree had fewer than $n!$ leaves ($L < n!$).

Since there are $n!$ distinct permutations in $S_n$, by the Pigeonhole Principle, there must exist at least one valid permutation $\pi^* \in S_n$ that does not appear on any leaf of the tree.

Now, suppose we provide the algorithm with an input array whose elements are ordered according to $\pi^*$. Because $\pi^*$ is absent from all leaves, the algorithm will traverse the tree and terminate at some leaf that outputs a different permutation $\pi \neq \pi^*$.

This output will fail to be sorted. Therefore, the algorithm cannot be correct. For an algorithm to sort every input correctly, every one of the $n!$ permutations must appear on at least one reachable leaf: $L \ge n!$. ■

4.4 Deriving the Fundamental Lower Bound

We now have two pieces of mathematical truth:

  1. From Theorem 4.1, a correct decision tree must have at least $n!$ leaves ($L \ge n!$).
  2. The worst-case running time of the algorithm is the height $h$ of the tree.

We now ask: what is the minimum possible height $h$ of a binary tree with $L$ leaves?

Lemma 4.1 (Maximum Leaves of a Binary Tree)

A binary tree of height $h$ has at most $2^h$ leaves:

$$L \le 2^h \tag{4.2}$$

Proof by Mathematical Induction:

Base Case ($h = 0$): A tree with height $0$ consists of a single root node, which is also a leaf. Thus $L = 1 = 2^0$. The base case holds.

Inductive Step: Assume that any binary tree of height $k$ has at most $2^k$ leaves. A binary tree of height $k + 1$ consists of a root connected to at most two subtrees, each of height at most $k$. By the induction hypothesis, each subtree has at most $2^k$ leaves: $$L \le 2^k + 2^k = 2 \times 2^k = 2^{k+1}$$ Thus the lemma holds for all non-negative integers $h$. ■

Synthesizing the Lower Bound

We can now combine Lemma 4.1 ($L \le 2^h$) and Theorem 4.1 ($L \ge n!$):

$$2^h \ge L \ge n! \implies 2^h \ge n! \tag{4.3}$$

Taking the base-2 logarithm of both sides (since $\log_2$ is a strictly increasing function):

$$h \ge \log_2(n!) \tag{4.4}$$

Because the height $h$ represents a discrete number of comparisons and must be an integer:

$$h \ge \lceil \log_2(n!) \rceil \tag{4.5}$$
The Information-Theoretic Lower Bound for Comparison Sorting

Theorem: Any comparison-based sorting algorithm requires at least: $$\lceil \log_2(n!) \rceil$$ comparisons in the worst case to sort $n$ elements.

4.6 Analytical Exercises

Problem 4.1 — Exact Lower Bounds for Small $n$
Calculate the theoretical comparison lower bound $\lceil \log_2(n!) \rceil$ for small arrays of size $n = 1, 2, 3, 4, 5$. Is it mathematically possible to sort $5$ elements using only $7$ comparisons in the worst case?

Calculations:

  • $n = 1: \quad 1! = 1 \implies \lceil \log_2(1) \rceil = 0$ comparisons.
  • $n = 2: \quad 2! = 2 \implies \lceil \log_2(2) \rceil = 1$ comparison.
  • $n = 3: \quad 3! = 6 \implies \lceil \log_2(6) \rceil = \lceil 2.585 \rceil = 3$ comparisons.
  • $n = 4: \quad 4! = 24 \implies \lceil \log_2(24) \rceil = \lceil 4.585 \rceil = 5$ comparisons.
  • $n = 5: \quad 5! = 120 \implies \lceil \log_2(120) \rceil = \lceil 6.907 \rceil = 7$ comparisons.

Question: Can 5 elements be sorted in 7 comparisons?
Yes! In 1959, Lester Ford and Selmer Johnson invented the Merge-Insertion Sort algorithm (also called the Ford-Johnson algorithm), which sorts 5 elements using at most 7 comparisons in the worst case, exactly matching the theoretical lower bound. ■

Problem 4.2 — Ternary Comparisons ($<, =, >$)
Suppose an oracle does not return just a boolean, but can distinguish equality in a single operation, returning one of three outcomes: $\{<, =, >\}$. What is the lower bound on the height of a ternary decision tree for sorting $n$ elements?

Derivation:

In a ternary tree, every internal node has at most $3$ children. By induction, a ternary tree of height $h$ can have at most: $$L \le 3^h \text{ leaves}$$

To sort $n$ distinct elements, all $n!$ permutations must still appear as leaves ($L \ge n!$). Therefore: $$3^h \ge n! \implies h \ge \log_3(n!) = \frac{\log_2(n!)}{\log_2(3)} \approx \frac{\log_2(n!)}{1.585}$$

Thus, ternary comparisons reduce the required height by a factor of $\log_2(3) \approx 1.585$, but the asymptotic complexity remains unchanged. ■

Summary & Transition

In this chapter, we derived the cornerstone theorem of comparison sorting:

  • Any comparison algorithm can be represented as a binary decision tree.
  • Correctness requires at least $n!$ leaves ($L \ge n!$).
  • A binary tree of height $h$ has at most $2^h$ leaves ($L \le 2^h$).
  • Combining these gives: $$h \ge \lceil \log_2(n!) \rceil$$

We now know that $\log_2(n!)$ is the universal speed limit for comparison sorting. But how does $\log_2(n!)$ grow as $n$ becomes large? Why does everyone say comparison sorting is $\Omega(n \log n)$?
