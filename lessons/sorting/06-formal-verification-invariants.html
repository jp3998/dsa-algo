Formal Verification: Preconditions, Postconditions, and Loop Invariants

"Testing can show the presence of bugs, but never their absence. To know that an algorithm sorts every conceivable input array correctly, we cannot rely on empirical trial. We must construct a mathematical proof using loop invariants and well-founded progress metrics."

6.1 The Engineering Problem: How Do We Know Code Is Correct?

In Part I, we proved what comparison algorithms cannot do: they cannot sort faster than $\Omega(n \log n)$ in the worst case.

Now, in Part II, we turn from impossibility to construction: how do we design algorithms that are mathematically guaranteed to sort correctly?

A novice programmer writes code, runs three test cases, sees that they pass, and assumes the program is correct. But in sorting, edge cases abound:

  • What happens when the array contains all identical values? ($[5, 5, 5, 5]$)
  • What happens when the array is already in reverse sorted order? ($[9, 8, 7, 6]$)
  • What happens when $n = 0$ (empty array) or $n = 1$ (single element)?

In 1969, British computer scientist Tony Hoare, building on the pioneering work of Robert Floyd, formulated Axiomatic Program Verification (known today as Floyd-Hoare Logic).

Definition 6.1 (The Hoare Triple)

A Hoare Triple describes how the execution of a piece of code alters the state of the computer: $$\{P\} \; C \; \{Q\} \tag{6.1}$$

  • Precondition ($P$): An assertion that must hold true about the program state immediately before executing code $C$.
  • Command ($C$): The sequence of instructions or algorithm being executed.
  • Postcondition ($Q$): An assertion that is guaranteed to hold true immediately after code $C$ terminates, provided $P$ was true initially.

The Hoare Triple for Sorting

Using the formal specification we established in Chapter 1, the entire problem of sorting an array $A$ can be written as a single Hoare triple:

$$\{A \text{ is an array of } n \text{ elements}\} \quad \text{Sort}(A) \quad \{A \text{ is sorted and is a permutation of its initial state}\}$$

More formally:

  • Precondition $P$: $A = A_{\text{init}}$ with length $n \ge 0$.
  • Postcondition $Q$: $$\left(\forall i \in \{0, \dots, n-2\}, \; A[i] \le A[i+1]\right) \quad \land \quad \left(\text{multiset}(A) = \text{multiset}(A_{\text{init}})\right)$$
Partial Correctness vs. Total Correctness

In formal logic, we distinguish between two levels of proof:

  1. Partial Correctness: If the algorithm halts, the final state satisfies postcondition $Q$. (It does not prove the code won't loop forever).
  2. Total Correctness: The algorithm is partially correct and it is mathematically guaranteed to terminate in finite steps.

$$\text{Total Correctness} = \text{Partial Correctness} + \text{Proof of Termination}$$

6.2 The Anatomy of a Loop Invariant

Most bugs in algorithms occur inside loops (especially while-loops and nested for-loops).

To prove that a loop is correct, we use a Loop Invariant.

Definition 6.2 (Loop Invariant)

A loop invariant is a formal mathematical predicate, denoted $I$, that is true prior to the first iteration of a loop and remains true before and after every subsequent iteration of the loop.

Proving correctness using a loop invariant is identical to Mathematical Induction:

The Three Invariant Obligations
  1. Initialization (Base Case):
    The invariant $I$ must be true before the very first iteration of the loop begins.
  2. Maintenance (Inductive Step):
    If the invariant $I$ is true before an iteration, and the loop continuation guard $G$ is true, then executing the loop body once leaves $I$ true before the start of the next iteration: $$\{I \land G\} \; \text{LoopBody} \; \{I\}$$
  3. Termination (Conclusion):
    When the loop terminates (the guard $G$ becomes False), the truth of the invariant $I$ combined with $\neg G$ must logically imply the postcondition $Q$: $$(I \land \neg G) \implies Q$$

6.3 Proving Termination: Loop Variants and Well-Founded Orders

A loop invariant proves that if the loop halts, it will produce the right answer. But what guarantees that the loop will ever halt?

To prove termination, we must define a Loop Variant Function (also called a progress metric or bound function).

Definition 6.3 (Loop Variant Function)

A loop variant is an integer-valued function $v : \text{State} \to \mathbb{Z}$ satisfying two conditions:

  1. Strict Monotonic Decrease: In every iteration of the loop, the value of $v$ strictly decreases: $$v_{k+1} < v_k \tag{6.2}$$
  2. Bounded Below: Whenever the loop continuation guard $G$ is true, the variant is non-negative: $$G \implies v \ge 0 \tag{6.3}$$

Why does this guarantee termination?
The natural numbers $\mathbb{N} = \{0, 1, 2, \dots\}$ possess the mathematical property of being well-founded: there is no such thing as an infinitely descending sequence of non-negative integers!

If $v$ starts at some finite integer (for example, $v_0 = n$) and decreases by at least $1$ with every iteration ($v_0 > v_1 > v_2 > \dots$), it must reach $0$ in at most $v_0$ iterations. Once $v$ reaches $0$, the loop guard $G$ cannot remain true, and the loop is forced to terminate!

6.4 The Spatial Anatomy of a Sorting Invariant

In sorting algorithms, the loop invariant almost always partitions the array into distinct geometric regions:

Notice how the variant metric relates directly to the size of the unprocessed region:

$$v(k) = n - k \tag{6.4}$$
  • At initialization ($k = 0$): $v = n - 0 = n$. The entire array remains to be processed.
  • During each iteration: $k$ increments by $1 \implies v$ decreases by $1$.
  • At termination ($k = n$): $v = n - n = 0$. The loop halts.

6.5 Analytical Exercises

Problem 6.1 — Formulating an Invariant for Array Maximum
Consider a simple algorithm that finds the maximum element in an array $A[0 \dots n-1]$: 
max_val = A[0]
for i from 1 to n - 1:
    if A[i] > max_val:
        max_val = A[i]
return max_val
Formulate the exact loop invariant, verify its Initialization, Maintenance, and Termination, and define a valid loop variant.

Formal Formulation:

  • Loop Invariant $I$: At the start of each iteration with loop index $i$, max_val holds the maximum value among all elements in the subarray $A[0 \dots i-1]$: $$I \equiv \left(\text{max\_val} = \max_{0 \le j < i} A[j]\right)$$
  • Loop Variant $v$: $v(i) = n - i$. Since $i$ increases by $1$ on each pass, $v$ decreases strictly until $v = 1$, when the loop halts.

Three Invariant Steps:

  1. Initialization: Prior to iteration $i = 1$, max_val = A[0]. The subarray $A[0 \dots 0]$ contains only $A[0]$, so max_val is trivially the maximum of this 1-element subarray. Invariant holds.
  2. Maintenance: Assume $I$ holds at the start of iteration $i$: $\text{max\_val} = \max(A[0 \dots i-1])$. The loop inspects $A[i]$. If $A[i] > \text{max\_val}$, max_val is updated to $A[i]$; otherwise, it remains unchanged. In either case, the new value of max_val equals $\max(A[0 \dots i])$. When $i$ increments for the next iteration, the invariant holds for the extended subarray.
  3. Termination: The loop terminates when $i = n$. Substituting $i = n$ into invariant $I$ gives: $$\text{max\_val} = \max_{0 \le j < n} A[j]$$ This matches the postcondition: max_val is the maximum of the entire array! ■
Problem 6.2 — Flawed Invariants and Off-By-One Errors
Suppose a student attempts to verify a sorting algorithm using the invariant: $$I_{\text{flawed}} \equiv \text{"Every element in } A[0 \dots k-1] \text{ has been compared to at least one other element."}$$ Explain why this invariant is mathematically insufficient to prove that the array is sorted upon termination.

Flaw Analysis:

An invariant must be strong enough to imply the postcondition upon termination.

When the loop terminates ($k = n$), the student's invariant states: "Every element in $A[0 \dots n-1]$ has been compared to at least one other element."

This statement fails to imply $A[i] \le A[i+1]$! For example, consider the array $[9, 4, 8, 2]$. If we compare $9$ with $4$, and compare $8$ with $2$, every single element has been compared to another element. Yet the array is completely unsorted!

An invariant must capture order relationships, not merely historical activity. ■

Summary & Transition to Elementary Sorting Algorithms

In this chapter, we established the mathematical verification toolkit:

  • Hoare Triples $\{P\} C \{Q\}$: Define the contract of what an algorithm must achieve.
  • Loop Invariants (Initialization, Maintenance, Termination): The inductive proof engine that guarantees correctness.
  • Loop Variants $v$: Strictly decreasing metrics on well-founded sets that guarantee termination.
