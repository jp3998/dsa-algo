What Exactly Is Sorting?

"Before we can analyze how an algorithm sorts, we must define what sorting actually means. What is the input? What is the output? And what rules make a proposed answer correct?"

1.1 The Specification Problem

When learning algorithms, it is tempting to jump straight to code: loops, pointers, and swaps. But in computer science, the first step is always specification: defining the problem so clearly that there is zero ambiguity about what counts as a correct solution.

If you ask someone on the street what sorting is, they might say: "arrange a list from smallest to largest." But what does that mean mathematically? If you want to write a program to check whether another program's output is correct, what tests must that output pass?

It turns out that a correct output must satisfy two completely separate requirements:

  1. The Order Requirement: The elements must be arranged in non-decreasing order.
  2. The Conservation Requirement: The output must contain the exact same elements as the input—nothing added, nothing deleted, and nothing replaced.
Definition 1.1 (The Sorting Problem)

Input: An array of $n$ elements: $$A = [a_0, a_1, \dots, a_{n-1}]$$ along with a comparison rule $\le$ that allows us to compare any two elements.

Output: An array: $$B = [b_0, b_1, \dots, b_{n-1}]$$ that satisfies two conditions:

Condition 1 (Order): Every element is less than or equal to the next element: $$\forall i \in \{0, 1, \dots, n-2\}, \quad b_i \le b_{i+1} \tag{1.1}$$

Condition 2 (Permutation / Conservation): Array $B$ is a rearrangement (a permutation) of array $A$. That is, there is a one-to-one mapping $\pi$ such that: $$b_i = a_{\pi(i)} \quad \text{for all } i \in \{0, 1, \dots, n-1\} \tag{1.2}$$

Why Do We Need Both Conditions?

Why isn't Condition (1.1) enough on its own?

Imagine a program that takes an input like $A = [17, 4, 29, 4, 11]$ and simply writes out: $$B = [0, 0, 0, 0, 0]$$ Notice that $0 \le 0 \le 0 \le 0 \le 0$. Condition (1.1) is 100% satisfied! Yet this answer is completely wrong because the original numbers were erased.

In mathematics, the input is called a multiset—a collection of items where duplicates matter (for example, the number $4$ appears twice in $A$). Condition (1.2) guarantees that our algorithm preserves this multiset: every original item must appear in the output with its exact original frequency.

1.2 What Is a Comparison Rule? (Understanding Orders)

In Definition 1.1, we assumed we have a comparison operator $\le$. But what properties must $\le$ actually have for sorting to even be possible?

If you think about it, a comparison rule only makes sense if it follows three basic, common-sense principles:

  1. Totality (No Incomparable Mysteries): Given any two items $x$ and $y$, you can always compare them. Either $x \le y$, or $y \le x$ (or both, if they are equal). You are never left with two items where the question "which is smaller?" has no answer.
  2. Transitivity (No Contradictions): If item $x$ is smaller than or equal to $y$, and $y$ is smaller than or equal to $z$, then $x$ must be smaller than or equal to $z$: $$(x \le y \land y \le z) \implies x \le z$$ Comparisons cannot wrap around in a circle.
  3. Reflexivity: Any item is less than or equal to itself ($x \le x$).
Definition 1.2 (Total Preorder vs. Total Order)

A comparison rule $\le$ that satisfies Reflexivity, Transitivity, and Totality is called a total preorder.

If it also satisfies Antisymmetry (meaning that if $x \le y$ and $y \le x$, then $x$ and $y$ are the exact same item, $x = y$), it is called a total order (or a linear order).

Why the distinction? In programming, we often sort items that have equal keys (like two people with the same age) even though they are different objects. That is why practical sorting operates on a total preorder.

Why Is Transitivity Necessary? The Rock-Paper-Scissors Paradox

To see why transitivity is not just abstract math, ask yourself: can we sort the items in a game of Rock-Paper-Scissors?

Suppose we try to treat "beats" as our comparison rule:

  • Rock beats Scissors ($R \succ S$)
  • Scissors beats Paper ($S \succ P$)
  • Paper beats Rock ($P \succ R$)

Notice what happens. If transitivity held, $R \succ S$ and $S \succ P$ would mean Rock must beat Paper. But Paper beats Rock! The rule contains a directed loop: $$R \longrightarrow S \longrightarrow P \longrightarrow R$$

Because of this loop, it is impossible to line up the three items from "best to worst." Whichever item you put first, the last item beats it!

This reveals a fundamental truth: sorting is only possible because transitivity forbids circular loops.

1.3 Duplicate Keys and Stability

In pure math, we often think of sorting simple numbers like $[3, 1, 7]$. But in software engineering, we almost always sort complex objects—such as spreadsheet rows, database records, or files.

When sorting complex objects, we usually sort by a specific field called the key:

  • Sorting students by Grade (the key is an integer).
  • Sorting files by Modification Date (the key is a timestamp).

What happens when two different records have the exact same key?

Suppose our input contains two records with key $7$:

Index 1: Record R₁ (Key = 7, Name = "Alice")
Index 3: Record R₄ (Key = 7, Name = "Bob")

In the input, Alice came before Bob ($1 < 3$).

When we sort the records by Key, both $[\text{Alice}, \text{Bob}]$ and $[\text{Bob}, \text{Alice}]$ have their keys in ascending order ($7 \le 7$). Both are mathematically sorted. But did the algorithm preserve their original relative order?

Definition 1.3 (Stability)

A sorting algorithm is called stable if, whenever two elements have equal keys, the element that appeared first in the input also appears first in the output.

Formally, if element $A[i]$ and element $A[j]$ have equal keys and $i < j$, then in the output sequence: $$\text{OutputPosition}(A[i]) < \text{OutputPosition}(A[j]) \tag{1.3}$$

Why Does Stability Matter in Practice?

Stability is essential for multi-column sorting.

Imagine you have a table of employees. First, you sort the table by First Name. Next, you sort the table by Department.

If your Department sort is stable, then within each Department, employees will still be listed alphabetically by First Name! The second sort did not scramble the work of the first sort.

If the sort were unstable, sorting by Department would randomly jumble the first names, forcing you to re-sort from scratch. Stability is also the mathematical foundation of Radix Sort, which we will derive in Chapter 22.

1.4 Analytical Exercises

To verify your understanding of these concepts, consider these two fundamental analytical problems.

Problem 1.1 — How Do Languages Check Equality With Only a "Less-Than" Operator?
In languages like C++ (std::sort) or Python, custom sort functions often only ask you to provide a strict "less-than" comparison (a < b), rather than <= or ==. How can an algorithm determine whether two items $a$ and $b$ are equal if it only has access to <?

Derivation:

Two items $a$ and $b$ have equal rank if and only if neither is strictly less than the other: $$\neg(a < b) \quad \text{and} \quad \neg(b < a)$$

In words: if $a$ is not smaller than $b$, and $b$ is not smaller than $a$, they must be tied!

In mathematics, this is called incomparability. A strict comparison operator $<$ that satisfies this consistency rule is called a strict weak ordering. This allows sorting algorithms to handle ties without needing a separate equality function. ■

Problem 1.2 — Can an Unstable Sort Always Be Made Stable?
Suppose you have an algorithm that is fast, but unstable. Can you always transform it into a stable algorithm without changing the core sorting code? What is the price in memory?

Derivation:

Yes. You can make any sorting algorithm stable by attaching each element's original index as a secondary key: $$\text{NewKey}(A[i]) = (\text{Key}(A[i]), \, i)$$

When comparing two items, you first compare their original keys. If the keys are tied, you break the tie by comparing their original indices: $$(\text{Key}(A[i]) = \text{Key}(A[j])) \implies (i < j \implies A[i] < A[j])$$

Because original indices are strictly unique ($i \neq j$), ties never occur. Thus, even an unstable sorting algorithm will preserve the original relative order.

The trade-off: Storing indices requires $\mathcal{O}(n)$ additional memory, and comparing composite pairs adds a small runtime overhead. ■

Summary & Transition

In this chapter, we established what sorting is:

  • It requires satisfying both Monotonic Order ($b_i \le b_{i+1}$) and Multiset Conservation ($B$ is a permutation of $A$).
  • It requires a comparison rule with Totality, Transitivity, and Reflexivity (a total preorder).
  • When duplicate keys exist, an algorithm is stable if it preserves the original relative order of tied items.

Notice what we have not discussed yet: how an algorithm actually finds this sorted arrangement.
