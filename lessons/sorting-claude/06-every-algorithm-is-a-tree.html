Lesson 06

Every comparison algorithm is a tree

Where we are

We have $2^k \ge n!$ — nearly a result, and not yet a proof. The trouble is that the argument followed a single run, while an algorithm is a rule covering every possible input, and its cost is what it does on the worst of them. We need a way to see all of an algorithm’s runs at once.

1 One run is a path

Take any comparison-based sorting algorithm, fix an input, and follow it.

It asks a first question. The question it asks is determined — it has not learned anything yet, so it has nothing to vary on. Every input of size $n$ gets the same first question.

Then an answer comes back, and the algorithm’s behaviour can differ for the first time. On one answer it asks a second question; on the other answer it may ask a different second question. Then a third, and so on, until it stops and announces an arrangement.

So a run is a sequence: question, answer, question, answer, …, answer, output. And what determines which sequence you get is entirely the answers, because the questions were fixed in advance by the algorithm.

The observation the whole lesson rests on

The algorithm chooses the questions. The input chooses the answers. Nothing else is in play.

2 All the runs at once

Now stop following one input and consider all of them together.

Every run begins at the same first question. Each of the two answers leads to a next question that is fixed by the algorithm. Each of those has two answers leading to two more fixed questions. Draw that and you have drawn a binary tree, without having intended to.

Definition

The decision tree of a comparison algorithm on inputs of size $n$ is the tree whose internal nodes are the comparisons it makes, whose two branches out of each node are the two possible answers, and whose leaves are the arrangements it outputs.

A root-to-leaf path is one run. The number of comparisons that run makes is the number of internal nodes on the path — its depth.

Figure 2.1 is the whole tree of an actual algorithm sorting three items. There are only six arrangements and the tree fits on a screen, which is the last time that will be true.

Three things to take from Figure 2.1, and the third is the one that matters.

The tree is the algorithm. Not a picture of it, not a summary — the tree contains every decision the algorithm will ever make on an input of this size. Two algorithms with the same tree are the same algorithm.

Different inputs take different paths, and paths have different lengths. This is why a single number cannot describe an algorithm’s cost without saying which inputs it is about.

The worst case is the height. The most comparisons this algorithm can be made to perform is the length of the longest root-to-leaf path, because some input travels that path. Not might travel it — the leaf at the bottom is an arrangement, and the input in that arrangement takes exactly that route.

Definition

The height of a decision tree is the number of comparisons on its longest root-to-leaf path. It is exactly the worst-case number of comparisons the algorithm makes.

3 Why every arrangement needs its own leaf

Now we start squeezing. The first squeeze is from below: the tree cannot be too small.

Claim

A correct comparison algorithm on $n$ distinct items has a decision tree with at least $n!$ leaves.

The argument is the one from Lesson 03’s last exercise, grown up. It is worth watching how it is found rather than only that it works.

We want to show there are many leaves. A leaf is where the algorithm commits to an output. So the question to ask is: can two different inputs end at the same leaf? If they can, we have no lower bound on leaves at all; if they cannot, the leaves must be at least as numerous as the inputs we care about.

So suppose two inputs in different arrangements do arrive at the same leaf. What goes wrong?

Proof

Suppose inputs $X$ and $Y$ are in different arrangements and both reach leaf $L$.

Reaching the same leaf means they answered every question along the path identically — that is what determines the route, and the route is what reached $L$.

At $L$ the algorithm outputs one arrangement. It is the same arrangement in both cases, because a leaf is a fixed point in a fixed tree: the algorithm at $L$ has no information beyond the answers on the path, and those were the same.

But $X$ and $Y$ need different outputs, since their items are arranged differently. So one of the two gets the wrong answer, and the algorithm is not correct — contradicting what we assumed about it.

Therefore no two different arrangements share a leaf. There are $n!$ arrangements, so there are at least $n!$ leaves.

Notice what the proof did not need. It never looked at which comparisons the algorithm chose, never assumed anything about its strategy, and would work equally well against an algorithm nobody has invented yet. That generality is the point: it is a statement about all correct algorithms, established without examining a single one.

4 How many leaves will a short tree hold?

The second squeeze comes from above: a tree of a given height cannot have too many leaves.

Count level by level. The root is one node. Each node has at most two children, so level 1 has at most 2 nodes, level 2 at most 4, level 3 at most 8. A tree of height $h$ therefore has at most $2^h$ nodes at its deepest level, and since every leaf sits at some level no deeper than $h$:

Claim

A binary tree of height $h$ has at most $2^h$ leaves.

And now the two squeezes meet, and Figure 4.1 shows them closing. At least $n!$ leaves are needed. At most $2^h$ are available. So

$$2^h \ge n!.$$

Which is the same inequality Lesson 05 reached by watching a candidate set shrink — and it is worth pausing on the fact that two quite different arguments produced it. One counted possibilities dying; this one counted leaves on a tree. They agree because they are describing the same constraint from opposite sides.

The difference is that this version is a proof about every algorithm. Lesson 05 followed a run and could not honestly say what happened on other inputs. The tree holds all the runs at once, so the height is a statement about the worst of them, and there is nowhere left for a clever algorithm to hide.

5 What we have, and what is missing

Collect the result.

Where Part I has got to

Any correct comparison-based sorting algorithm on $n$ distinct items has a decision tree of height $h$ with $2^h \ge n!$. Its worst-case number of comparisons is that height. Equivalently, taking logarithms,

$$h \ge \log_2(n!).$$

That is exact, it holds for every algorithm of this kind, and it was obtained without inventing one.

It is also, right now, nearly useless — and being honest about that is more valuable than the result itself.

Ask yourself what $\log_2(n!)$ is when $n$ is a million. Is it about a million? Ten million? A billion? Unless you have met this before, you have no idea, and neither does the inequality tell you. We have exchanged one quantity we could not picture, $n!$, for another we cannot picture, $\log_2(n!)$.

So there is arithmetic to do, and it is the last piece of the argument. That is the next lesson, and at the end of it the bound finally says something you can hold in your head.

The idea in one line

An algorithm is not one run but a whole tree of them: the algorithm picks the questions, the input picks the route, the worst case is the height — and since every arrangement needs a leaf of its own, the tree cannot be short.

Check yourself

Figure 2.1’s tree has six leaves and height 3. Could a cleverer algorithm sort three items with a tree of height 2?

No, and the bound settles it immediately.

A tree of height 2 has at most $2^2 = 4$ leaves. Three items have $3! = 6$ arrangements, each needing its own leaf. Four is fewer than six, so no such tree exists — whatever the algorithm does, two arrangements would share a leaf and one would get the wrong output.

Height 3 gives up to 8 leaves, which is enough room for 6. And the algorithm in Figure 2.1 achieves it, so 3 is not only permitted but reached.

Worth noticing what this did not require: we did not consider any particular clever algorithm. The counting rules them all out at once.

The tree in Figure 2.1 has 8 possible positions at depth 3 but only 6 leaves. Is the algorithm wasting two of them?

No — the missing positions are unreachable, and that is forced.

Look at where the tree stops early. Along the path where $A < B$ and $B < C$, the algorithm outputs immediately after two questions. It could ask about $A$ and $C$, but the answer is already determined: chaining gives $A < C$, so every surviving candidate agrees, and the question would split the candidate set into everything and nothing.

This is Lesson 05’s second exercise appearing as a structural fact about the tree. A node whose candidates all agree has one real branch and one impossible one, so the tree is narrower there than the $2^h$ ceiling allows.

And this is exactly why the bound is a bound rather than an equality. $2^h$ counts positions a binary tree could have. Transitivity means a decision tree often cannot fill them, so the real trees are worse than the ceiling — which only makes the lower bound safer.

Where exactly in the proof of Section 3 was correctness used? What would break if the algorithm were allowed to be wrong occasionally?

In the final step, and everything would break.

The proof establishes that two inputs reaching the same leaf receive the same output, then concludes that this is impossible. That last move is exactly where correctness enters: it is only a contradiction if the algorithm is required to be right on both inputs.

Drop that and the bound collapses. An algorithm allowed to be wrong can have a tree of height 0: one leaf, no questions, always answers ABC. On one input in six it is right.

This is worth holding on to because it is the escape hatch that real algorithms sometimes take. Anything that sorts approximately, or is right with high probability, or is allowed to fail on rare inputs, is not bound by this argument — it is playing a different game. When you meet a claim that seems to beat a lower bound, check first whether it has quietly relaxed correctness.

Suppose someone shows you a decision tree with exactly $n!$ leaves, all at the same depth. Have they found an optimal sorting algorithm?

They have found something that looks optimal, and you should check that it is a decision tree of a real algorithm at all.

The bound says a tree needs at least $n!$ leaves and gets at most $2^h$ of them. A tree with exactly $n!$ leaves all at one depth would be as small as the counting permits.

But drawing such a tree is not the same as exhibiting an algorithm. Every internal node has to be a genuine comparison between two specific items, and both its branches have to be reachable — there must be surviving arrangements that answer each way. The previous exercise showed that transitivity often makes one branch impossible, and a node like that is not a node, it is a pass-through.

So the honest position after this lesson: we know no algorithm can beat $\log_2(n!)$, and we do not know whether any algorithm attains it. The counting cannot tell us — a bound never promises that it is reachable. That question stays open until Part V, where it is settled by building something.

What’s still unanswered

We have $h \ge \log_2(n!)$, proved for every correct comparison-based algorithm. The reasoning is finished. The arithmetic is not.

As it stands the bound is a shape rather than a quantity. Nobody knows what $\log_2(n!)$ is by looking at it, and a limit you cannot evaluate cannot be compared against an algorithm you might build.

So the next lesson does one thing: works out how big $\log_2(n!)$ actually is. It is an honest piece of arithmetic with a genuinely surprising answer — and when it lands, the number that comes out is the one that has been governing this subject the whole time.
