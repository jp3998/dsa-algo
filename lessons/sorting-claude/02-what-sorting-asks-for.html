Part I · Order and Information

Lesson 02

What sorting asks for

Where we are

We know what an ordering relation has to do, and we proved that a good one picks out exactly one row. What we still do not have is a statement of the job. Last lesson closed on a procedure that ignores its input completely and hands back a handful of numbers in increasing order — and every condition we had written so far accepts it. This lesson repairs that, and the repair hands us the object the rest of Part I is built on.

1 Why a specification comes first

We are about to spend a long time building algorithms. Before any of that, we need something that sounds almost too modest to bother with: a test that takes an input and a proposed output and reports correct or incorrect.

It is worth being clear about why that has to come first.

You cannot build towards a target you cannot recognise. Every claim we will make for the next forty lessons — this algorithm works, this one is faster, this one cannot be beaten — is a claim about meeting a standard. If the standard is vague, the claims are noise. And the specification has a second job that matters every bit as much: when an algorithm is wrong, the specification is the thing that says so, and says where.

So: what exactly is being asked for?

2 The obvious answer, and what it misses

Here is the answer almost everyone gives first, and it is half right:

First attempt

The output is correct when it is in order.

Test it. Input: 17, 4, 29, 4, 11. Proposed output: 1, 2, 3, 4, 5.

That output is in order. It passes. It is also absurd — the answer contains nothing that was in the question.

Work Figure 2.1 for a minute before reading on. Press Replace an item and you get the failure we started this section with — an output in perfect order that has lost something. Press Shuffle and you get the mirror image: every item still present, sitting in the wrong places.

The two tests move independently. Neither one implies the other, and neither one alone is worth anything.

So the specification needs two clauses, not one, and the second is the one that gets forgotten because it feels like it goes without saying. It does not. Saying it turns out to take some care.

3 “The same items” is harder than it sounds

We want to say: the output contains the same items as the input. The natural first move is to talk about the set of items and require the two sets to be equal.

That fails, and it fails on something completely ordinary.

Input: 3, 3, 7. Proposed output: 3, 7.

The set of items in the input is $\{3, 7\}$. The set of items in the output is $\{3, 7\}$. Equal. The test passes — and a 3 has gone missing.

A set records only which items are present. It has no way to say how many times, because $\{3, 3, 7\}$ and $\{3, 7\}$ are the same set. Every duplicate collapses, and duplicates are exactly what we need to keep track of.This is a good example of a tool quietly discarding the thing you needed. Sets are the reflex reach for “a collection of items,” and here the reflex throws away the data the problem is about.

So we need a collection that counts:

Definition

A multiset is a collection in which each item has a multiplicity — the number of times it occurs. Two multisets are equal when they contain the same items with the same multiplicities.

Under that test, 3, 3, 7 and 3, 7 are different, which is what we wanted. Order is still ignored, which is also what we want at this stage: this clause is about what is there, and a separate clause will handle where it sits.

4 Rearrangement, and the object it names

There is a second way to say the same thing, and it is the one we will actually use. Rather than comparing what the two collections contain, describe what happened to the items.

Nothing was created. Nothing was destroyed. Every item in the output is an item from the input, moved to a new position — and each one moved to its own position, with no two landing on top of each other and no position left empty. The output is a rearrangement of the input.

That pattern of arrows in Figure 4.1 is itself a thing, separate from the items it moves. Give it a name:

Definition

A sequence $B$ of length $n$ is a permutation of a sequence $A$ of length $n$ when there is a one-to-one pairing of the positions $1, \dots, n$ with the positions $1, \dots, n$ such that each output position holds the item from the input position it is paired with.

Writing that pairing as $\pi$, the condition is $B[i] = A[\pi(i)]$ for every $i$, where $\pi$ hits every position exactly once.

Now, an honest remark, because this is a place where books often let two ideas blur together. For sequences of the same length, “$B$ has the same multiset as $A$” and “$B$ is a permutation of $A$” are the same condition. Neither is stronger. Any output passing one passes the other.

So why prefer the second? Because of what it gives us to hold.

  • The multiset view describes what is there. It answers the question we asked, and then it is finished.
  • The permutation view describes how things moved. It makes the rearrangement into an object in its own right — one that exists independently of the particular items, and, crucially, one you can count.

That last word is doing quiet work. Once a permutation is an object, asking “how many are there?” becomes a legitimate question with a definite answer. And the answer to that question is where Part I starts to get its teeth — it is the whole of Lesson 04, and everything after it leans on the number that comes out.

5 The specification

Both halves are in hand. Put them together.

The sorting problem

Given: a sequence $A$ of $n$ items, and an ordering relation $\preceq$ on those items.

Produce: a sequence $B$ of length $n$ such that

  1. $B$ is a permutation of $A$; and
  2. $B[i] \preceq B[i+1]$ for every $i$ from $1$ to $n-1$.

What is given is the precondition — what we may assume. What is produced is the postcondition — what we promise. Every correctness argument in this series has that shape: assume the precondition, run the procedure, show the postcondition holds. It is worth noticing the shape now, while the example is small enough to see all of.

Both clauses are load-bearing, and it takes one example each to show it. Delete clause 1 and the output 1, 2, 3 walks straight through. Delete clause 2 and the input itself walks through unchanged. Neither clause is decoration.

These two clauses are exactly the two tests that were running in Figure 2.1. What was described there in plain words — the same items, and each no greater than the next — is what clauses 1 and 2 say precisely.

One detail in clause 2 deserves a second look, because it is doing more than it appears to.

It only mentions neighbours. But what we actually want — the promise from Lesson 01 — is that every pair sits the right way round, including items at opposite ends. Clause 2 never mentions those pairs at all.

It does not need to. If each item is no greater than the next, then chaining along the sequence puts every earlier item no greater than every later one. That is transitivity, from Lesson 01, and this is the second time it has handed us something for free.The first time was in Lesson 00, where six questions about neighbours settled all twenty-one pairs. It is the same fact, appearing once as a saving in what we must check and once as a saving in what we must write down.

Where this stops being true

Clause 2 is a shorthand that only works because the relation is transitive. Drop transitivity and the clause would have to be written out in full — every pair, not every neighbour — and it would be a different and much larger condition. We are allowed the short version because of a property we spent a section of Lesson 01 earning.

6 How many correct answers are there?

We can now ask something we could not ask before, because we finally have a test to apply: given an input, how many different outputs pass it?

When no two items are tied, exactly one. Clause 1 fixes which items appear, and Lesson 01 proved that a relation with no ties admits exactly one valid row of those items. So there is one correct answer and the phrase the sorted sequence is honest.

When items are tied, more than one. Two tied items can appear in either order, and both resulting sequences satisfy both clauses. We saw this at the end of Lesson 01; the specification inherits it rather than fixing it.

Which brings us to the version of this that actually bites.

The items being sorted are rarely bare numbers. They are usually records — a person with a name and a score, a transaction with a time and an amount — and the relation looks at one field and ignores the rest. Figure 6.1 is four such records sorted by score.

Two records that tie on the field being compared are still different records. They have different names. And the specification, which only ever sees the field the relation looks at, cannot tell them apart and has no view about which should come first.

The situation

The specification is silent exactly where the relation is silent. When tied items are distinguishable in some way the relation does not see, several outputs are correct, and the specification has no opinion about which one you produce.

Notice the shape of this. It is not a flaw we should rush to patch. The specification says what it says, accurately, and a procedure that produces any of those outputs has done what was asked. Whether you are satisfied depends on something you never told the relation about.

We are going to leave it there on purpose. The tools to say anything more precise do not exist yet — we have no algorithms, so we cannot talk about what a particular one does with ties. When they exist, this comes back with a name and turns out to be worth a great deal.

The idea in one line

Sorting promises two things at once — these same items, and this order — and the specification is the conjunction. Keep only the second half and 1, 2, 3 is a valid answer to every question.

Check yourself

Three broken procedures. (a) Ignores the input and returns $1, 2, \dots, n$. (b) Returns the input untouched. (c) Removes duplicates, then orders what is left. Which clause does each violate?

(a) violates clause 1. Its output is in order, so clause 2 is satisfied. But the items are not the input’s items, so it is not a permutation of the input.

(b) violates clause 2, unless the input happened to arrive sorted. Its output is certainly a permutation of the input — the one that moves nothing — so clause 1 is satisfied.

(c) violates clause 1, and this is the one worth dwelling on. Its output is in order, and it contains only items that were in the input, and every distinct input item appears. It feels as though it should pass. It fails because the multiplicities changed: an input with two 3s produces an output with one, so no one-to-one pairing of positions exists. This is exactly the case that killed the set-based test in Section 3.

Clause 2 constrains only neighbouring pairs. Why is that enough — and how would the clause have to be written if the property doing the work were missing?

Transitivity is doing the work. From $B[1] \preceq B[2] \preceq \dots \preceq B[n]$, chaining gives $B[i] \preceq B[j]$ for every $i < j$. The $n-1$ stated conditions imply all $n(n-1)/2$ of them.

Without transitivity the clause would have to read: for every $i < j$, $B[i] \preceq B[j]$. Not a stylistic difference — it is a condition of a different size, and it would change what verification costs, since there would be no way to confirm an answer without examining every pair.

The general point, which keeps returning: a shorthand is never free. It is always being paid for by a property of the thing it describes, and it is worth knowing which property.

Is “$B$ has the same multiset as $A$” a weaker condition than “$B$ is a permutation of $A$”?

No — for sequences of the same length they are the same condition. Each implies the other.

If $B$ is a permutation of $A$, then each item of $A$ appears in $B$ exactly once for each time it appeared in $A$, so the multisets match. Going the other way, if the multisets match then each item can be paired up with its own copies, and collecting those pairings gives a one-to-one map of positions.

The reason we favour the permutation phrasing is not logical strength. It is that it names the rearrangement itself. “The same multiset” is a statement about two collections and stops there. “A permutation” introduces an object — the pairing $\pi$ — that can be studied, compared to other permutations, and counted. Lesson 04 does the counting, and the result is the foundation of everything in Part I after it.

Your input has ten items and all ten tie with each other under the relation. How many outputs satisfy the specification?

All of them — every one of the $10! = 3{,}628{,}800$ rearrangements.

Check it against the two clauses. Clause 1: any rearrangement of the input is a permutation of the input, so all of them pass. Clause 2: it asks that each item be no greater than the next, and since every pair ties, every pair satisfies that in both directions. So clause 2 constrains nothing at all.

Two things worth taking from this. First, the number of correct answers is not a fixed property of the problem — it depends on the input, and it ranges from exactly one to everything. Second, and more interesting: in this input the relation carries no information whatsoever. Every comparison returns the same uninformative answer, and an algorithm could ask questions all day and be no closer to distinguishing one output from another. It does not need to be, because they are all correct.

That connection — between how much the relation can tell you and how many answers remain possible — is not a coincidence. It is the machinery of the next several lessons.

A procedure sorts records by score correctly, but when two records tie it puts them in a different order each time it runs. Does it satisfy the specification? Should you be happy?

It satisfies the specification completely. Every output it produces is a permutation of the input and is in non-decreasing order by score. There is no clause it breaks, and no amount of staring at the specification will find one.

Whether you should be happy is a separate question, and the specification cannot answer it because it never had the information. The relation was told about scores. It was never told that the records arrived in a meaningful order, or that a person would read the names, or that yesterday’s report should match today’s.

The honest conclusion is that the specification is under-constrained for some uses and exactly right for others. If you need more, you have to ask for more — either by adding a requirement about what happens to tied items, or by enriching the relation so the ties disappear.

Both of those are real options with real costs, and we will meet each of them. The first acquires a name in Part V, where it falls out of an algorithm rather than being demanded.

What’s still unanswered

We can now judge an answer. Hand us an input and a proposed output and we can say correct or incorrect, and point at the clause that fails.

An algorithm cannot do that. It never gets to see a proposed output next to the specification and compare them — it has to build the output, and it starts knowing nothing about which arrangement is the right one. All it can do is ask questions and act on the answers.

Which raises the question we have been circling since Lesson 00 without ever asking directly: what is an algorithm actually allowed to ask, and how much does an answer tell it? Until we pin that down, every claim about what sorting costs is a claim about nothing in particular.
