Lesson 3

What exactly is the sorting problem, and what may an algorithm do?

Stage 0 · Foundations

Where we are

Lessons 1 and 2 gave us a comparison we can trust: a strict weak ordering, supplied in Python by <, a key function, or a comparator that honours its contract. We know what a sorted arrangement is and how many there are.

This course is about what sorting costs. Before we can ask that, three things must be pinned down. Why would anyone pay for sorting at all? What exactly counts as a correct answer? And what is an algorithm allowed to do to find one? The third matters more than it seems: until it is fixed, “cost” has no meaning.

  • Lesson 1 §05: exactly one sorted arrangement
  • Lesson 1 §06: ties and tiers
  • Lesson 2 §01: Python asks only <

Prerequisite check

P1

How many sorted arrangements does a strict total order on 5 elements have?

Exactly one (lesson 1, Theorem 7): the first position is forced to hold the minimum, and so on.
120 = 5! counts all arrangements. Only one of them has nothing out of order.
In a total order every pair is related. Which element is forced into the first position?

P2

Python’s sorted is given a comparison that is not a strict weak ordering. What happens?

  • It returns some rearrangement of the input, with no error; which one depends on the starting order.
    That is what CPython did with NaN, tolerance and cyclic comparators (lesson 2, §05).
  • It raises a ValueError.
    Python does not check the comparison. It trusts it and returns whatever its steps produce.
  • It returns the input unchanged.
    Sometimes, by accident (the NaN example); but other starting orders gave other outputs.
  • It sorts correctly anyway, because it compares every pair.
    No sort compares every pair; sorts rely on transitivity to skip most pairs, which is exactly why a broken comparison misleads them.

01Why pay for order?

Sorting will cost something, and most of this course is about how much. So first: what does a sorted list buy? Two everyday questions show it.

Duplicates. Does any value occur twice? More precisely: are any two elements tied? Without order, the natural method compares every pair, \(n(n-1)/2\) of them, because a tie could be hiding anywhere. In a sorted list, ties cannot hide. Lesson 1, Theorem 10 says that each tier forms one contiguous block, so two tied elements always stand next to each other somewhere, and checking neighbours is enough:

Lemma 1 (ties are neighbours)

A sorted list contains two tied elements if and only if some neighbour pair is tied. Checking this takes \(n - 1\) comparisons: for neighbours with \(b_{i+1} \not< b_i\) (true in a sorted list), they are tied exactly when also \(b_i \not< b_{i+1}\).

Proof

Tiers appear as contiguous blocks (lesson 1, Theorem 10). If a tier has two elements, its block has two adjacent positions. The converse is immediate. One comparison per neighbour pair suffices because sortedness already rules out \(b_{i+1} < b_i\).

Search. Is a value \(v\) present, and where would it go? In an unsorted list, \(v\) could belong anywhere, so in the worst case every element must be examined. In a sorted list, one comparison of \(v\) with the middle element tells us which half \(v\) belongs in, and the other half can be ignored from then on. Repeat on the half that is left. How many comparisons does that take?

Predict first

A sorted list holds 1000 values. A value \(v\) could belong in any of the 1001 gaps (before the first element, between two neighbours, after the last). Each comparison of \(v\) with an element of the list rules out, at best, half of the remaining gaps. How many comparisons are needed to pin down the gap?

Right: \(2^{9} = 512 < 1001 \le 1024 = 2^{10}\).
That is the cost of examining every element one by one, which is what an unsorted list forces.
Halving is faster than that: each comparison halves what is left, rather than removing a fixed amount.
Nine halvings leave \(1001 / 2^9 \approx 2\) gaps, not one.
How many times must you halve 1001 to get down to 1?

Ten. Each comparison at best halves the set of remaining gaps, so after \(k\) comparisons at least \(1001 / 2^k\) remain in the worst case, and we need \(2^k \ge 1001\), that is \(k \ge \log_2 1001 \approx 9.97\). Halving achieves this: 10 comparisons suffice. The halving procedure needs care to get exactly right (its boundaries are a classic source of bugs), and lesson 12 builds it properly, with its invariant.

The answer for 1000 values, ten, is a logarithm, and logarithms will appear in almost every lesson from now on. The course reads them in two ways, and both have just appeared: the first describes what the search did, the second explains why no method that asks yes/no questions can do better.

  • Halvings. \(\log_2 m\) is the number of times \(m\) must be halved to reach 1. That is what the search did: each comparison halved the remaining gaps, from 1001 down to 1, in \(\lceil \log_2 1001 \rceil = 10\) rounds. Whenever an algorithm repeatedly halves its problem, a logarithmic number of rounds follows.
  • Bits. \(k\) yes/no answers have at most \(2^k\) combinations, so singling out one of \(m\) possibilities takes at least \(\log_2 m\) answers proof. A comparison is a yes/no answer, so \(\log_2 m\) is a floor on the number of comparisons that single out one of \(m\) possibilities. For the search, \(m = 1001\) gaps, so no method can always succeed with fewer than ten comparisons: halving is as good as it gets.

Sorting is an investment: paid once, it turns later questions into a scan or a lookup intuition. Whether it pays depends on how many questions follow and how much sorting costs, which is the question of the rest of the course.

02The specification

Before we can ask what sorting costs, we need to know exactly what counts as success. “A function that sorts” sounds clear until you try to test one.

Predict first

Each function below claims to sort a list of numbers. Select every one that is a correct sorting function for all inputs.

  • def f(a): return []
    The empty list is trivially in order (no pair is out of order), but every element is lost: ordered, yet not a rearrangement of the input.
  • def f(a): return list(range(len(a)))
    0, 1, …, n−1 is in order, but these are not the input’s elements: ordered, wrong elements.
  • def f(a): return [min(a)] * len(a)
    In order and the right length, but every element is replaced by a copy of the minimum: ordered, but not the same elements.
  • def f(a): return a
    Exactly the right elements, but in their original order: a rearrangement (the trivial one), not ordered.
  • def f(a): return sorted(set(a))
    Correct whenever all values are distinct, but set removes duplicates: [2, 1, 2] gives [1, 2], so it fails on inputs with duplicates.
  • def f(a): return sorted(a)
    This one is correct: ordered, and a rearrangement of the input.

Every fake passes half of a two-part test. (a), (b) and (c) produce something in order but lose or invent elements. (d) keeps the elements but does not order them. (e) passes on distinct values and fails on duplicates, so it is wrong for some inputs, which makes it wrong. A correct specification needs both halves.

Definition (the sorting problem)

Precondition. A list \(a = [a_0, \ldots, a_{n-1}]\) and a comparison \(<\) that is a strict weak ordering.

Postcondition. A list \(b = [b_0, \ldots, b_{n-1}]\) such that

  1. \(b\) is sorted: there are no \(i < j\) with \(b_j < b_i\) (by lesson 1, Lemma 11, equivalently \(b_{i+1} \not< b_i\) for every \(i\));
  2. \(b\) is a permutation of \(a\): there is a bijection \(\pi\) of \(\{0, \ldots, n-1\}\) with \(b_i = a_{\pi(i)}\) for every \(i\).

Read \(\pi\) as instructions for building the output: slot \(i\) of \(b\) receives the element that sat at position \(\pi(i)\) of \(a\). “Bijection” means every input position is used exactly once, so nothing is lost and nothing is copied. For example, sorting \(a = [30, 10, 20]\) uses \(\pi(0) = 1\), \(\pi(1) = 2\), \(\pi(2) = 0\), which gives \(b = [10, 20, 30]\).

Condition 2 is phrased with positions, not values, so that duplicates are counted correctly: \(b\) must contain each element exactly as often as \(a\) does. That is precisely what fake (e) violates.

xs.sort() rearranges the list in place: its final contents must be \(b\). sorted(xs) returns a new list \(b\) and leaves xs alone. The specification is the same.

How many candidate outputs are there?

Lemma 2 (counting arrangements)

A list of \(n\) elements has exactly \(n!\) arrangements \(b = [a_{\pi(0)}, \ldots, a_{\pi(n-1)}]\), one for each bijection \(\pi\).

Proof

Choose \(\pi(0)\) in \(n\) ways, then \(\pi(1)\) among the \(n - 1\) positions left, and so on: \(n (n-1) \cdots 1 = n!\).

With distinct keys, no two elements tie, so every tier of the strict weak ordering holds a single element, and the ordering is a strict total order. By lesson 1, Theorem 7, exactly one of these \(n!\) arrangements is sorted. So, in its plainest form:

Sorting \(n\) distinct elements means finding the one sorted arrangement among \(n!\) candidates.

With ties there are \(n_1! \cdots n_k!\) sorted arrangements (lesson 1, Theorem 10), and the specification accepts any of them. (Python promises a particular one, the stable one, as lesson 7 explains.)

Ties change how many answers are acceptable, but not what the problem is about. For the first analyses it pays to remove them: with distinct keys the answer is unique, every pair of elements is settled one way or the other, and counts come out clean. So we assume, for now:

Assumption A1 (distinct keys)

Until stated otherwise, all keys are distinct, so \(<\) is a strict total order on the elements and the sorted output is unique. Lessons 7, 25 and 33 drop this assumption deliberately. Every algorithm will still be tested on duplicates among its edge cases.

Checkpoint 1

Q1

How many arrangements does a list of 6 distinct elements have?

\(6! = 720\), and exactly one of them is sorted.
\(6^2\) counts pairs of positions. An arrangement chooses an element for each of 6 positions, without reuse: \(6 \cdot 5 \cdot 4 \cdot 3 \cdot 2 \cdot 1\).
\(6^6\) allows an element to be used several times. A permutation uses each exactly once.
1 + 2 + … + 6 adds the choices instead of multiplying them.
Choose the first element (6 ways), then the second (5 ways), and so on.

Q2

The list [2, 2, 1, 1, 1] has \(5! = 120\) arrangements, counted as bijections \(\pi\) of positions. How many of them are sorted?

Tiers {1, 1, 1} and {2, 2}: \(3! \cdot 2! = 12\). As a list of values all 12 look the same, [1, 1, 1, 2, 2], but they move different elements to each position. The difference matters as soon as elements carry more than their key, as records do; lesson 7 returns to it.
As values, there is only one sorted list. But the specification counts bijections of positions: the three 1s can be arranged among themselves in \(3!\) ways and the two 2s in \(2!\) ways.
That counts every arrangement, most of which put a 2 before a 1.
Use lesson 1, Theorem 10: multiply \(n_i!\) over the tiers.
Which tiers are there, and how many internal orders does each have?

Q3

When does sorted(set(a)) meet the specification?

  • Exactly when a has no duplicates.
    With distinct values, set removes nothing and the result is the sorted arrangement. With a duplicate, the output is shorter than the input, which violates condition 2.
  • Always: it returns a sorted list.
    Sorted is only condition 1. Condition 2 requires every element, with its multiplicity.
  • Never: set destroys the order.
    The order of the set does not matter, since sorted imposes one. On distinct values the result is exactly right.
  • Only when a is already sorted.
    Sortedness of the input is irrelevant; duplicates are what break it.

03What may an algorithm do?

We are about to ask what sorting costs. The answer depends entirely on what counts as one step. If calling sorted(a) counts as one step, sorting costs one step, and the question is empty. And if the keys are small integers that an algorithm may use as list indices, it can learn where an element belongs from its value alone, without comparing it with anything, and the answer changes again (lesson 30 explores exactly this). So “cost” means nothing until we fix two things: what an algorithm may do to learn about the input, and what we charge for.

Definition (the comparison model)

  • The algorithm receives the list and its length \(n\). It cannot look inside the elements.
  • To learn anything about the elements it may only ask: is \(a_i < a_j\)? Each such question is one comparison, with a yes/no answer.
  • It may move elements: copy them, swap them, store them in other lists. Moves are counted separately (as moves), and they never reveal anything about the elements.
  • Everything else, such as arithmetic on indices, loops, and memory for indices and counters, is allowed and is not counted as comparisons.
  • Cost measure (for now): the number of comparisons.

Why this model?

  • Generality. An algorithm that only asks < sorts anything with a valid <: numbers, strings, tuples, records by key.
  • Python’s sort lives in it. It asks only < (lesson 2, §01).
  • Comparisons are what is expensive in Python intuition. Each one dispatches through __lt__ or a key; moving a list element just copies a reference. Lesson 29 measures this.

What the model leaves out is just as important: looking at digits or bits of a key, arithmetic on keys, using a key as an index, hashing. These are real operations, and the model excludes them on purpose. Every lower bound proved in this model holds only in this model. When an algorithm later seems to “beat” one of them, the first question will be which of these exclusions it ignored.

Common question · Can’t I detect duplicates in linear time with a set?

len(set(a)) < len(a) hashes each element, which reads its representation; that is outside the comparison model. Its running time depends on how the hash function behaves on your keys, which is an assumption about the keys, not a guarantee. Both models are legitimate; they answer different questions. Within the comparison model, detecting duplicates turns out to be essentially as hard as sorting, a fact we will be able to prove once we have lower bounds.

The model has a consequence that simplifies everything that follows.

Predict first

A sorting algorithm in the comparison model runs on [10, 30, 20] and then on [1, 99, 50]. Will it ask the same comparisons, in the same order?

  • Yes, always.
    Right. Why? See below.
  • Not necessarily: the values differ.
    The values differ, but look at what the algorithm can find out about them.
  • Only if the algorithm is simple.
    No simplicity is needed. See below.

Both lists have the same pattern: the first element is the smallest, the second the largest, the third in the middle. Every question “is \(a_i < a_j\)?” gets the same answer on both lists. An algorithm that can learn only through such questions cannot tell the lists apart.

Lemma 3 (only the pattern matters)

Let \(a\) and \(a'\) be lists of length \(n\) with \(a_i < a_j \iff a'_i < a'_j\) for all \(i, j\). A deterministic algorithm in the comparison model asks the same comparisons in the same order on both, receives the same answers, and performs the same moves. In particular it outputs the same arrangement \(\pi\).

Proof

Induction on the number of steps taken. Before the first step the algorithm knows only \(n\), the same for both lists. Suppose the first \(t\) steps were identical. The algorithm’s next step is determined by \(n\) and the answers received so far, which are the same; so it is the same step. If it is a comparison of positions it has tracked identically, the answer is the same by assumption. If it is a move, it moves the elements at the same positions, so the elements’ positions stay in correspondence.

Lemma 3 lets us replace any input by something simpler. With distinct keys, write each element’s rank in its place: 0 for the smallest, \(n-1\) for the largest. [10, 30, 20] and [1, 99, 50] both become [0, 2, 1]. An input and its list of ranks give the same answer to every question “is \(a_i < a_j\)?”, so by Lemma 3 an algorithm runs identically on both: the same comparisons, the same moves, the same cost. There are exactly \(n!\) such rank patterns, the permutations of \(0, \ldots, n-1\). They are the only inputs we ever need to consider.

One more definition before we count anything. An algorithm usually needs different numbers of comparisons on different inputs of the same size: in §04 below, Python’s own sort needs 999 comparisons on one list of 1000 numbers and about 8 600 on another. So “its cost for \(n\) elements” is not a single number until we say how to summarise over the inputs. The two simplest summaries are the most it ever needs, a guarantee that no input can break, and the least.

Definition (worst and best case)

For an algorithm \(A\) and input \(x\), let \(C_A(x)\) be the number of comparisons \(A\) makes on \(x\). The worst case is \(W_A(n) = \max C_A(x)\) and the best case is \(B_A(n) = \min C_A(x)\), both over all inputs \(x\) of size \(n\); by Lemma 3, over the \(n!\) rank patterns.

(Averages need a stated probability distribution over inputs; they wait until lesson 10, which introduces one.)

Checkpoint 2

Q4

Which of these is not allowed in the comparison model?

  • Ask whether a[3] < a[5].
    That is the one question the model allows; it costs one comparison.
  • Swap a[3] and a[5].
    Moves are allowed. They are counted separately, and they reveal nothing about the elements.
  • Compute a[3] % 10.
    This reads the element’s value. The model treats elements as opaque; arithmetic on keys is excluded on purpose (lesson 30 lifts this restriction).
  • Store the index 5 in a variable.
    Bookkeeping on indices is free.

Q5

Why may we analyse only inputs that are permutations of \(0, \ldots, n-1\)?

  • Because of Lemma 3: the algorithm behaves identically on all inputs with the same rank pattern, and with distinct keys every input has one of these \(n!\) patterns.
    That is the whole justification, and it relies on the model: an algorithm that reads digits could tell [10, 30, 20] from [1, 99, 50].
  • Because real inputs are usually small integers.
    Real inputs can be anything: strings, records, floats. The reduction works because the algorithm cannot see the values, not because the values are integers.
  • Because Python converts elements to integers before sorting.
    Python does no such thing; it only asks <.
  • Because duplicates never occur.
    Duplicates are excluded here by Assumption A1, but that is a separate assumption. The reduction to rank patterns is about what a comparison algorithm can observe.

Q6

An algorithm makes 3 comparisons on [5, 1, 4]. How many does it make on [50, 10, 40]?

  • Exactly 3, the same ones.
    Same rank pattern [2, 0, 1], so Lemma 3 applies.
  • It depends on the algorithm.
    For any deterministic comparison algorithm, Lemma 3 forces the same run.
  • More, because the numbers are larger.
    The size of the numbers is invisible in this model.
  • Fewer, because the gaps are larger.
    Gaps between values are invisible too; only the answers to < matter.

04Watching a real sort count

The comparison model is not an abstraction Python ignores; we can watch Python’s own sort inside it. Wrap each element in an object whose __lt__ counts how often it is called.

Predict first

Python’s sorted is given 1000 numbers that are already sorted. How many comparisons does it make?

  • 0: it notices nothing needs doing.
    It cannot notice without comparing. See below.
  • 999
    Right. See below.
  • About 10 000
    That is roughly what it uses on random input. See below.
  • 499 500
    That would be every pair. See below.

Three observations to carry forward:

  • On sorted input Python uses exactly \(n - 1\) comparisons: one per neighbour pair, the number lesson 1 needed just to check sortedness. Lesson 5 shows that no algorithm can do with fewer, even one that only checks.
  • Reversed input costs the same \(n - 1\). Lesson 34 explains how Python’s sort notices it.
  • Random input costs far fewer than every pair, but far more than \(n - 1\). Where between those does the true cost of sorting lie? That question drives lessons 4 to 16.

These are measurements of one implementation on particular inputs empirical: another Python version, or other inputs, may give other numbers.

05In Python: testing a sort

The specification gives a test harness directly: check both halves, on many small inputs, including duplicates, against Python’s own sorted. This “stress test” catches most sorting bugs in minutes and is worth having in any contest or interview preparation.

is_permutation uses Counter, which hashes the elements: it is outside the comparison model. That is fine: the harness is a test of a sort, not part of one. Note the small value range in stress_test: it makes duplicates common, which is where many sorting bugs hide.

E1

A sorted list has 50 elements. How many comparisons does Lemma 1’s method use to decide whether two elements are tied?

One per neighbour pair: 49.
50 elements have 49 neighbour pairs.
Two comparisons per pair would be needed in an unsorted list. In a sorted list \(b_{i+1} < b_i\) is already ruled out, so one comparison per pair decides.
That is every pair, \(\binom{50}{2}\): the cost without order.

A sorted list holds 1 000 000 values, so a new value could belong in any of 1 000 001 gaps. How many halving comparisons are needed in the worst case?

\(2^{19} = 524\,288 < 1\,000\,001 \le 1\,048\,576 = 2^{20}\).
\(2^{19} = 524\,288\) is less than 1 000 001: nineteen halvings leave about two gaps.
That is the cost of scanning. Halving needs only the logarithm.

E4

An algorithm makes 3 comparisons on the sorted input of size 4 and 6 on every other input of size 4. What are its best and worst case for \(n = 4\)?

  • \(B(4) = 3\), \(W(4) = 6\).
    Best and worst case are the minimum and maximum over all inputs of the size.
  • \(B(4) = W(4) = 6\), since only one input is cheaper.
    The best case is a minimum over inputs; one cheap input is enough to make it 3.
  • The average, \((3 + 23 \cdot 6)/24\).

Ledger

Established

  • In a sorted list, tied elements are neighbours, so \(n-1\) comparisons detect a tie proof §01
  • Singling out one of \(m\) possibilities with yes/no answers needs at least \(\log_2 m\) of them, and halving achieves \(\lceil \log_2 m \rceil\) when every answer can halve proof §01
  • Specification: the output is sorted and a permutation of the input; there are \(n!\) candidates and, for distinct keys, exactly one is sorted proof §02
  • The comparison model; a deterministic comparison algorithm behaves identically on inputs with the same rank pattern, so \(n!\) patterns are all the inputs there are proof §03
  • CPython 3.12’s sort uses \(n - 1\) comparisons on sorted and on reversed input of size 10, 100 and 1000, and far fewer than \(n(n-1)/2\) on random input empirical §04

Assumptions in force

  • Model: comparison model; cost = number of comparisons; worst case unless stated.
  • Keys: A1, all keys distinct, so \(<\) is a strict total order.

Lenses in use

  • None formally yet. Two seeds: a comparison is a yes/no answer worth at most one bit (§01), and Python’s real sort can be measured in comparisons (§04).

Reasoning tools acquired

  • A specification as precondition and postcondition; testing both halves.
  • Reducing inputs to rank patterns (only possible because of the model).
  • Logarithms as halvings and as bits.
  • Instrumenting comparisons; stress-testing against sorted with many duplicates.

The task and the rules are now exact: find the one sorted arrangement among \(n!\), learning only through comparisons. What is the simplest algorithm that is certainly correct, and how many comparisons does it make?
