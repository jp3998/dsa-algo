Lesson 4

What is the simplest certainly-correct way to sort, and what does it waste?

Stage 0 · Foundations

Where we are

Lesson 3 made the task exact: find the one sorted arrangement among \(n!\) candidates (Assumption A1: distinct keys), learning about the elements only by asking “is \(a_i < a_j\)?”, and paying one unit per question. Lesson 1 gave a way to check a candidate: \(n - 1\) neighbour comparisons.

That is already enough to write an algorithm. This lesson builds the most direct one, proves it correct, derives exactly what it costs, and then asks the question that will organise the whole course: what does the algorithm know at each moment, and does it use it?

P2

What is the worst-case cost \(W_A(n)\) of an algorithm \(A\)?

  • The largest number of comparisons \(A\) makes on any input of size \(n\).
    A maximum over all inputs (by lesson 3, Lemma 3, over the \(n!\) rank patterns).
  • The number of comparisons on the reversed input.
    For some algorithms the reversed input is a worst case, but that has to be proved; the definition is a maximum over all inputs.
  • The average number of comparisons over all inputs.
    That is an average, which needs a stated distribution (lesson 10). The worst case is a maximum.
  • The number of comparisons needed to sort any input by the best possible algorithm.
    That is a property of the problem, not of one algorithm. We will get there (lesson 15); \(W_A\) is about algorithm \(A\).

01The most direct idea

We have two facts. Exactly one of the \(n!\) arrangements is sorted (lesson 1, Theorem 7). And checking whether one arrangement is sorted costs at most \(n - 1\) comparisons (lesson 1, Lemma 8). The most direct algorithm follows: generate the arrangements one by one, check each, and stop at the first that passes.

Predict first

Right: all \(4! = 24\), if the sorted arrangement happens to be generated last.
That is the best case: the first candidate generated happens to be the sorted one.
Half is a reasonable guess for an average, but in the worst case the sorted arrangement can be the very last one.
3 is the cost of checking one candidate. The question is how many candidates.
How many arrangements of 4 elements are there, and where in the sequence could the sorted one be?

All 24, if the sorted arrangement comes last. Which inputs put it last depends on the order in which arrangements are generated, so to analyse the algorithm we must fix that order.

02Construction

Three ingredients.

  1. Generate every arrangement exactly once. Python’s itertools.permutations(a) yields the \(n!\) arrangements of a as tuples. It works on positions, not values, and yields them in lexicographic order of the position tuples: for \(n = 3\), positions (0,1,2), (0,2,1), (1,0,2), (1,2,0), (2,0,1), (2,1,0).
  2. Check a candidate with neighbour comparisons, stopping at the first neighbour pair that is out of order. To respect Python’s convention, ask only <: “is \(b_{i+1} < b_i\)?”
  3. Return the first candidate that passes.

This algorithm is usually called permutation sort, or brute-force sort.

Going deeper · Its randomised cousin

Instead of generating arrangements in order, one could shuffle at random until the result is sorted (“bogosort”). It can examine the same arrangement many times and has no worst-case bound at all: for any number \(N\), there is a positive probability that the first \(N\) shuffles all fail proof. Its expected cost needs the tools of lesson 10. The enumerating version at least guarantees termination.

04Correctness

Specification (lesson 3): given a list a and a strict weak ordering <, return a sorted permutation of a.

Finding the argument. What is true each time the loop moves on to a new candidate? Every candidate examined so far failed the check. What does failing mean? By lesson 1, Lemma 11, “some neighbour pair is out of order” is equivalent to “not sorted”, because < is a strict weak ordering. So the loop maintains a simple fact: every candidate examined so far is not sorted. That fact alone does not prove anything; what we need are three separate claims about the value returned and one about termination.

Theorem 1 (permutation sort is correct)

For every list a and every strict weak ordering <, permutation_sort(a) returns a sorted permutation of a.

Proof

It returns a permutation. Every candidate is an arrangement of the positions of a.

What it returns is sorted. It returns a candidate only when is_sorted returned True, that is, when no neighbour pair is out of order. Since < is a strict weak ordering, lesson 1, Lemma 11 makes that equivalent to sorted.

It returns. The candidates are all \(n!\) arrangements, finitely many, generated one per iteration (termination measure: the number of arrangements not yet generated, which drops by 1 each iteration). At least one arrangement is sorted (lesson 1, Theorem 10; with distinct keys, Theorem 7), and it passes the check. So the loop reaches a passing candidate and returns it, possibly an earlier passing one.

The proof never used distinctness: the algorithm is correct with ties, because the check asks “is \(b_{i+1} < b_i\)?” and not “is \(b_i < b_{i+1}\)?”.

Stress. Two plausible mistakes, and where the proof catches each one.

  1. Checking strict increase: if not b[i] < b[i + 1]: return False. With distinct keys this is equivalent. With a tie, two equal neighbours fail the check, so no candidate passes; the loop ends and the function returns None. On [2, 1, 2] it returns None. The proof breaks at “the sorted arrangement passes the check”: with ties, a sorted arrangement need not be strictly increasing.
  2. Stopping one pair early: for i in range(len(b) - 2). The last neighbour pair is never compared, so on [1, 3, 2] the very first candidate passes and [1, 3, 2] is returned. The proof breaks at “passes the check implies sorted”: Lemma 11 needs every neighbour pair.

Edge cases proof (each follows from the proof; the builder also runs them):

  • []: permutations([]) yields one empty tuple, which passes: returns [], 0 comparisons.
  • [x]: returns [x], 0 comparisons.
  • All equal, [5, 5, 5]: the first candidate passes after 2 comparisons.
  • Already sorted: the first candidate passes after \(n - 1\) comparisons.
  • Duplicates, [2, 1, 2]: returns [1, 2, 2] after 3 candidates and 5 comparisons.

05Cost

What to count. Comparisons, the measure of the model. We also count candidates, because the cost per candidate turns out to be small and the number of candidates is what explodes. (Generating each candidate also copies \(n\) element references into a new tuple; those moves are not counted as comparisons, but they are real work.)

Best case. Every call ends with a candidate that passes, and a passing candidate costs exactly \(n - 1\) comparisons. On sorted input the very first candidate passes. So \(B(n) = n - 1\) for \(n \ge 1\) proof.

Worst case.

Predict first

How many comparisons does permutation sort make on the reversed input [4, 3, 2, 1]?

Right. The derivation below shows where 40 comes from.
24 is the number of candidates. Each costs at least one comparison, and some cost more.
72 = 24 × 3 assumes each candidate costs the full 3 comparisons. Most fail at the first or second neighbour pair.
Two questions: how many candidates are examined, and how many comparisons does each cost?

Forty. Here is the derivation, in four steps.

Step 1: which candidates are examined? In [4, 3, 2, 1] the sorted arrangement takes positions (3, 2, 1, 0) in that order, which is the last tuple in lexicographic order. So every one of the 24 candidates is examined.

Step 2: what does one candidate cost? The check makes comparison number \(j\) (of positions \(j-1\) and \(j\), for \(j = 1, \ldots, n-1\)) exactly when all earlier comparisons answered “no”, that is, when the first \(j\) entries of the candidate are increasing.

Step 3: add over all candidates. How many of the \(n!\) arrangements of distinct elements have their first \(j\) entries increasing? Choose which \(j\) elements go first, \(\binom{n}{j}\) ways; they must appear in increasing order, 1 way; the rest go in any order, \((n-j)!\) ways. That is \(\binom{n}{j}(n-j)! = n!/j!\). So comparison \(j\) is made on \(n!/j!\) candidates, and the total over all candidates is

\[ T(n) \;=\; \sum_{j=1}^{n-1} \frac{n!}{j!}. \]
proof

Read it back: the \(j\)-th term counts candidates that survive long enough to be asked their \(j\)-th question. Sanity check, \(n = 3\): \(6/1 + 6/2 = 9\). For \(n = 4\): \(24 + 12 + 4 = 40\).

Step 4: no input is worse. For any input of distinct elements, the candidates are the same \(n!\) arrangements of its values, and Step 3 applies to them unchanged: the total cost of checking all of them is \(T(n)\), whatever the input. An input stops somewhere in that sequence, so it costs at most \(T(n)\); the reversed input stops at the very end.

Theorem 2 (exact cost)

With distinct keys, permutation sort makes \(B(n) = n - 1\) comparisons in the best case (sorted input) and \(W(n) = T(n) = \sum_{j=1}^{n-1} n!/j!\) in the worst case (reversed input). Moreover \(T(n) < 2 \cdot n!\).

Proof

The best and worst cases were derived above. For the bound, write \(T(n) = n!\,\bigl(\tfrac{1}{1!} + \tfrac{1}{2!} + \cdots + \tfrac{1}{(n-1)!}\bigr)\). Since \(j! \ge 2^{j-1}\) (each of the factors \(2, \ldots, j\) is at least 2), each term is at most \(1/2^{j-1}\), and the bracket is less than \(1 + \tfrac12 + \tfrac14 + \cdots = 2\).

Read it back. Checking costs fewer than two comparisons per candidate on average over the candidates: most fail at the first or second neighbour pair. The explosion comes entirely from the number of candidates.

Going deeper · The constant is e − 1

The bracket \(\sum_{j \ge 1} 1/j!\) converges to \(e - 1 \approx 1.71828\), because \(e = \sum_{j \ge 0} 1/j!\). So \(T(n)/n! \to e - 1\) proof sketch; Table 2 shows it agreeing to four decimals by \(n = 8\).

For scale: \(T(20) \approx 4.18 \times 10^{18}\). At a billion comparisons per second (an assumed rate, not a measurement), that is about 132 years, to sort 20 numbers.

    For [2, 3, 4, 1] the sorted order takes positions (3, 0, 1, 2), which comes late in lexicographic order; for [1, 4, 3, 2] it takes (0, 3, 2, 1), which comes early. The algorithm never measures disorder at all.

    Both have exactly 3 out-of-order pairs. Disorder is the wrong lens for this algorithm.
  • The second input is closer to sorted, so the check passes sooner.
    Every failing candidate is checked from scratch; nothing carries over from the input’s own order except the position of the answer in the sequence.
  • Random variation.
    The algorithm is deterministic. The same input always gives the same count.

06What it knows, and what it wastes

The cost is absurd. But where exactly does the waste come from? Not from the check, which costs fewer than two comparisons per candidate. It must come from the comparisons themselves: some of them, it seems, tell the algorithm nothing it did not already know. To make “already know” precise, we need to say what the algorithm knows at each moment.

Predict first

Right: after 3. The last 4 comparisons teach it nothing.
It only stops after 7. Watch the diagram in Fig. 1: when does it become a single chain?
After 2 comparisons it knows 2 < 3 and 1 < 3, but not yet how 1 and 2 compare.
Track which pairs have been compared, and what follows from them by transitivity.

The first three questions are 3 < 2? (no), 1 < 3? (yes), 1 < 2? (yes). After them the algorithm knows 1 < 2 < 3, the whole order. It then examines two more candidates, (3, 2, 1) and (3, 1, 2), that contradict what it already knows, and asks four more questions whose answers it already has.

What exactly does the algorithm know? Each comparison returns one fact, \(x < y\) or \(y < x\). Facts also combine: from \(1 < 2\) and \(2 < 3\) the algorithm may conclude \(1 < 3\) without asking, by transitivity. Nothing else can be learned in the comparison model: the elements themselves are invisible (lesson 3, §03).

Lesson 1 already has the object that holds exactly this kind of information. A set of facts “\(x\) before \(y\)”, together with everything transitivity adds, is a strict partial order (no cycles can arise, since the facts are true of one real input), the kind lesson 1 drew as a Hasse diagram. And the arrangements consistent with a partial order are its linear extensions, \(e(P)\) of them. So the natural guess is: what the algorithm knows is a partial order, and the inputs it cannot yet rule out are its linear extensions. Fig. 1 has been drawing exactly this partial order below the stepper. The guess is right:

Theorem 3 (knowledge is a partial order)

Let \(O\) be the outcomes of the comparisons made so far on some input with distinct keys, and \(P\) the strict partial order they generate (their transitive closure). Then:

(a) the inputs (rank patterns) that would have produced exactly these outcomes are those whose sorted order is a linear extension of \(P\); there are \(e(P)\) of them;

(b) if \(x\) and \(y\) are unrelated in \(P\), some input consistent with \(O\) has \(x < y\) and another has \(y < x\).

Proof

(a) A rank pattern is a strict total order on the elements. It produces the observed outcomes exactly when it agrees with every outcome in \(O\). A total order is transitive, so agreeing with \(O\) is the same as agreeing with everything \(O\) implies, that is, with \(P\); and a total order agreeing with \(P\) is precisely one whose sorted arrangement is a linear extension of \(P\).

(b) Adding \(x \prec y\) to \(P\) creates no cycle, because a cycle through the new pair would need \(y \prec x\) in \(P\) already. By lesson 1, Corollary 6, some linear extension puts \(x\) before \(y\). Symmetrically, some puts \(y\) before \(x\). By (a), both are consistent inputs.

Read it back. At any moment the algorithm’s knowledge is a partial order \(P\): the facts it observed and their consequences, nothing more. The inputs it still cannot rule out number \(e(P)\). It can be certain of the sorted order exactly when \(e(P) = 1\), that is, when \(P\) has become a total order. A comparison whose answer is already in \(P\), because the same pair was asked before or because transitivity implies it, cannot change \(P\): it teaches nothing.

This is the knowledge lens, and it will be the main lens of the course. For every algorithm we will ask: what partial order does it hold, what shape does it have, and does each comparison change it?

Through this lens, permutation sort wastes in two ways:

  • It asks questions it can already answer. On the reversed input of size 4 it makes 40 comparisons, but only \(\binom{4}{2} = 6\) pairs exist: at least 34 of its comparisons ask about a pair already asked. It has the full order after comparison 24 and keeps going for 16 more.
  • It tests candidates its knowledge has already ruled out. On [2, 3, 1] it knew the answer after 3 comparisons and still checked two candidates that contradicted it.

The algorithm treats each candidate as a fresh question and forgets everything between candidates.

07Remember what you learn

The waste suggests the fix: never ask a question you can already answer. The bluntest way to follow it: ask about every pair exactly once. With distinct keys every pair is related one way or the other, so after asking all of them the algorithm knows the whole strict total order: \(e(P) = 1\). What remains is pure bookkeeping, turning that knowledge into the one sorted arrangement.

How do we turn “all pairs known” into an arrangement? Look at the answer we are aiming for. By lesson 1, Theorem 7, the sorted arrangement is \(x_0 \prec x_1 \prec \cdots \prec x_{n-1}\): the element at position \(r\) has exactly \(r\) elements before it, all smaller, and all the others after it, all larger. So an element’s position is simply the number of elements smaller than it. So, for each element, count how many elements are smaller: its rank.

Why the else? With distinct keys, if \(a_j < a_i\) is false then \(a_i < a_j\), so each pair awards one point to its larger element.

Invariant (after the double loop)

rank[i] equals the number of elements \(a_j\) with \(a_j < a_i\).

Theorem 4 (comparison counting)

With distinct keys, rank_sort returns the sorted permutation of a and makes exactly \(n(n-1)/2\) comparisons on every input.

Proof

Each pair \(\{i, j\}\) is compared exactly once and gives one point to its larger element, which proves the invariant. If \(x < y\), everything smaller than \(x\) is also smaller than \(y\), and so is \(x\) itself; so rank(\(x\)) < rank(\(y\)). Hence the \(n\) ranks are distinct numbers in \(\{0, \ldots, n-1\}\), so they are exactly \(0, \ldots, n-1\): every slot of b is written exactly once, which makes b a permutation of a. And smaller elements get smaller positions, so b is sorted. The comparison count is the number of pairs, \(\binom{n}{2}\), whatever the input.

Knuth calls this comparison counting. Compare the costs: for \(n = 10\), permutation sort’s worst case is 6 235 300 comparisons; comparison counting always uses 45. The entire gap is the value of remembering.

Stress: ties. Theorem 4 assumed distinct keys. What if they are not?

Predict first

What does rank_sort([5, 5, 5]) return?

  • [5, 5, 5]
    Right; see why below.
  • [5, None, None]
    That is what a “more careful” version returns. See below.
  • It raises an IndexError.
    No index goes out of range. See below.

It returns [5, 5, 5], correctly. For a tied pair \(i < j\), a[j] < a[i] is false, so the else gives the point to a[j], the later element. Ties are broken by position: the code really ranks by the pair (key, position), which is a strict total order by lesson 2, Theorem 2. So the ranks are still distinct, the proof goes through unchanged, and as a bonus tied elements keep their input order (the property lesson 7 calls stability).

Now the tempting “more careful” version, which awards no point on a tie:

if a[j] < a[i]:
    rank[i] += 1
elif a[i] < a[j]:
    rank[j] += 1

On [5, 5, 5] all ranks stay 0, every element is written to b[0], and the result is [5, None, None]: not a permutation. The proof fails at “the ranks are distinct”. The else was not a shortcut; it was the tie-breaking rule.

But are all \(n(n-1)/2\) questions needed? Comparison counting never uses transitivity: it asks every pair, even when the answer follows from earlier answers. On a sorted input of 4 elements, the 3 neighbour questions \(a_0 < a_1\), \(a_1 < a_2\), \(a_2 < a_3\) already prove the whole order (lesson 1, Lemma 8); the other 3 answers are consequences. How few questions can possibly suffice?

08In Python

In practice neither is how you sort: sorted(a) is. Permutation sort is a baseline that frames sorting as a search among \(n!\) candidates; comparison counting is occasionally useful when \(n\) is tiny and you need each element’s rank anyway (its stable tie-breaking is a plus). Both are stepping stones.

E3

Why is the reversed input a worst case for permutation sort?

  • Its sorted arrangement is the last one generated, and the total cost of checking all \(n!\) candidates is the same \(T(n)\) for every input.
    Both halves are needed: the first says the reversed input checks everything; the second says checking everything is the maximum any input can cost.
  • It has the most out-of-order pairs.
    The algorithm never looks at disorder; Q2 showed two inputs with equal disorder and very different costs. The reversed input is worst because of where its answer sits in the generation order.
  • Every candidate fails at the last neighbour pair.
    Most candidates fail at the first or second pair; that is why \(T(n) < 2 \cdot n!\).
  • Because \(n!\) is the largest factorial.
    The count of candidates is \(n!\) for every input; what varies is how many of them are examined.

Ledger

Established

  • Permutation sort is correct for any strict weak ordering proof §04
  • Its best case is \(n - 1\) comparisons (sorted input) and its worst case is \(T(n) = \sum_{j=1}^{n-1} n!/j! < 2 \cdot n!\) (reversed input) proof; \(T(n)/n! \to e - 1\) proof sketch §05
  • Its cost depends on where the answer sits in the generation order, not on how disordered the input is proof, by example §05
  • Knowledge theorem: after any comparisons, the algorithm’s knowledge is a partial order \(P\); the inputs still possible are the \(e(P)\) linear extensions; unrelated pairs can still go either way proof §06
  • Comparison counting sorts with exactly \(n(n-1)/2\) comparisons on every input, correctly with ties thanks to its tie-breaking by position proof §07

Assumptions in force

  • Comparison model; cost = comparisons, worst case; A1 (distinct keys) for the cost results; the correctness results allow ties.

Lenses in use

  • Knowledge (introduced): what the algorithm knows is a partial order; \(e(P)\) counts what it still cannot rule out; comparisons whose answers are known or implied teach nothing. So far it has explained why permutation sort wastes almost all of its work.

Reasoning tools acquired

  • Correctness as three claims (permutation, sorted, returns) plus a decreasing termination measure.
  • Stress-testing a proof by finding where a buggy variant breaks it.
  • Exact counting by asking “on how many candidates is comparison \(j\) made?”.
  • Bounding a sum by a geometric series.
  • The knowledge view: partial order, linear extensions, wasted comparisons.

Open gaps

Open question

Asking every pair costs \(n(n-1)/2\) comparisons, yet on a sorted input the \(n - 1\) neighbour answers already prove the whole order. How many comparisons are truly necessary?
