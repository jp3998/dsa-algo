Lesson 4

What is the simplest certainly-correct way to sort, and what does it waste?

Stage 0 · Foundations

Where we are

Lesson 3 made the task exact. With distinct keys (Assumption A1), sorting means finding the one sorted arrangement among \(n!\) candidates, learning about the elements only by asking “is \(a_i < a_j\)?”, and paying one unit for each question. And lesson 1 gave us a way to check any candidate: \(n - 1\) neighbour comparisons.

Put those two facts side by side and you can already write a sorting algorithm. It won’t be a good one, but that isn’t the point yet. In this lesson we’ll build the most direct algorithm we can, prove that it is correct, and work out exactly what it costs. Then we’ll ask the question that will organise the rest of the course: at each moment, what does the algorithm actually know, and does it use it?

Depends on

  • Lesson 1 §05–06: neighbour checks suffice
  • Lesson 1 §04: linear extensions, Corollary 6

Prerequisite check

P1

At most how many neighbour comparisons does it take to check whether an arrangement of 6 distinct elements is sorted?

Yes, 5. A row of 6 elements has five places where two neighbours meet, and lesson 1, Lemma 8 says that checking those five pairs is enough: if each one is in order, chaining them puts every pair in order. The check can stop sooner, but only when it finds a pair out of order.
15 is the number of all pairs, \(\binom{6}{2}\). You don’t need them all: if every neighbour pair is in order, every other pair follows by chaining neighbours together, by transitivity (lesson 1, Lemma 8). So only the 5 neighbour pairs get asked.
That counts the elements rather than the gaps between them. Six elements in a row have five neighbour pairs, (0,1) up to (4,5), just as six fence posts have five gaps.
720 is \(6!\), the number of possible arrangements. But here you’re holding one arrangement and checking just that one, which only takes its neighbour pairs.
Picture the six elements in a row and count the places where two neighbours meet. Each of those is one comparison, and lesson 1 showed that they are all you need.
The check compares neighbours only. So the real question is: how many neighbour pairs does a row of 6 elements have?
Write the pairs by position: (0,1), (1,2), … The last element sits at position 5. Where does the list end?

Number the positions 0 to 5. The neighbour pairs are (0,1), (1,2), (2,3), (3,4) and (4,5): five of them, one fewer than the elements, because each pair is a gap between two neighbours. Why are these enough? Lesson 1, Lemma 8: for distinct elements, if every neighbour pair is in order, then any earlier element is smaller than any later one, by chaining the neighbour facts in between. So the check asks at most 5 questions, and fewer if it meets a pair out of order and stops early.

The tempting wrong answers count something else. 6 counts elements, not gaps. 15 counts every pair, \(\binom{6}{2}\), but the other 10 follow from the neighbours by transitivity. And 720 counts arrangements, not the comparisons needed to check one.

P2

What is the worst-case cost \(W_A(n)\) of an algorithm \(A\)?

  • The largest number of comparisons \(A\) makes on any input of size \(n\).
    Yes. The worst case is a maximum: run \(A\) on every input of size \(n\) and take the biggest count. By lesson 3, Lemma 3, the count depends only on the input’s rank pattern, so that maximum is over the \(n!\) patterns.
  • The number of comparisons on the reversed input.
    The reversed input is a natural suspect, and for some algorithms it really is a worst case. But that’s something you have to prove about a particular algorithm; it isn’t the definition. The definition takes the maximum over all inputs, whichever input turns out to reach it.
  • The average number of comparisons over all inputs.
    That’s the average case, a different measure. An average needs a stated distribution over the inputs (lesson 10), and it is often smaller than the worst case. The worst case is the single largest count.
  • The number of comparisons needed to sort any input by the best possible algorithm.
    That describes the problem, not algorithm \(A\): how few comparisons any algorithm at all could get by with, which we’ll study in lesson 15. \(W_A(n)\) is about one specific algorithm and how badly it can do.
Notice the subscript \(A\): this cost belongs to one particular algorithm. Now, “worst” over what?
Imagine running \(A\) on every input of size \(n\) and writing down each comparison count. Which single number from that list is the worst case?

Fix the algorithm \(A\) and the size \(n\). Each input of size \(n\) makes \(A\) perform some number of comparisons. By lesson 3, Lemma 3, that number depends only on the input’s rank pattern, so there are at most \(n!\) different counts to look at. The worst case \(W_A(n)\) is the largest of them: option (a).

The other options are close relatives, which is why they tempt. (b) picks one particular input; it may or may not reach the maximum, and for each algorithm that has to be proved. (c) is the average of the counts, which is never larger than the maximum and needs a distribution as well. (d) moves from one algorithm to all algorithms: that’s the cost of the problem itself, a question for lesson 15.

01The most direct idea

Let’s take stock of what we have. Exactly one of the \(n!\) arrangements is sorted (lesson 1, Theorem 7). And checking whether a given arrangement is sorted costs at most \(n - 1\) comparisons (lesson 1, Lemma 8). So here is the most direct plan imaginable: generate the arrangements one at a time, check each one, and stop at the first that passes. It’s guaranteed to work, because the sorted arrangement is in there somewhere. The only question is how long it takes to find it.

Predict first

That’s it: all \(4! = 24\) of them, in the unlucky case where the sorted arrangement is generated last.
That’s the best case, when the very first arrangement generated happens to be the sorted one. The worst case asks how unlucky we could get.
Half is a sensible guess for a typical input, but the worst case is about the unluckiest one: the sorted arrangement could be the very last one generated.
3 is what it costs to check one candidate, its three neighbour pairs. Here we’re counting how many candidates might need checking.
How many arrangements of 4 elements are there, and where in the sequence could the sorted one sit?

All 24, if the sorted arrangement happens to come last. And which inputs put it last? That depends on the order in which we generate the arrangements, so before we can analyse anything, we have to fix that order.

02Construction

So we need three ingredients, and each one is something we already have, or nearly.

  1. A way to generate every arrangement exactly once. Python’s itertools.permutations(a) does exactly this: it yields the \(n!\) arrangements of a as tuples. It works on positions, not values, and it produces them in lexicographic order of the position tuples. For \(n = 3\) the order is (0,1,2), (0,2,1), (1,0,2), (1,2,0), (2,0,1), (2,1,0).
  2. A check for each candidate, using lesson 1’s neighbour test and stopping at the first neighbour pair that is out of order. To match Python’s convention it asks only <: “is \(b_{i+1} < b_i\)?”
  3. Return the first candidate that passes.

This algorithm is usually called permutation sort, or brute-force sort.

Going deeper · Its randomised cousin

Instead of generating arrangements in order, one could shuffle at random until the result is sorted (“bogosort”). It can examine the same arrangement many times and has no worst-case bound at all: for any number \(N\), there is a positive probability that the first \(N\) shuffles all fail proof. Its expected cost needs the tools of lesson 10. The enumerating version at least guarantees termination.

04Correctness

It looks right on that example, but one example isn’t a proof. Let’s prove that it works on every input. First, recall what “works” means. The specification from lesson 3 says: given a list a and a strict weak ordering <, return a sorted permutation of a.

How do we find the argument? A good habit is to ask what stays true while the loop runs. Each time the loop moves on to a new candidate, we know that every candidate examined so far failed the check. And what does failing mean? It means some neighbour pair was out of order, which, because < is a strict weak ordering, is the same as “not sorted” (lesson 1, Lemma 11). So the loop keeps one simple fact true: every candidate it has thrown away really was wrong.

That fact is reassuring, but on its own it doesn’t prove that the answer is right. For that we need two claims about what the function returns (it is a permutation, and it is sorted), plus a third: that it returns at all.

Theorem 1 (permutation sort is correct)

For every list a and every strict weak ordering <, permutation_sort(a) returns a sorted permutation of a.

Proof

It returns a permutation. Every candidate is an arrangement of the positions of a.

What it returns is sorted. It returns a candidate only when is_sorted returned True, that is, when no neighbour pair is out of order. Since < is a strict weak ordering, lesson 1, Lemma 11 makes that equivalent to sorted.

It returns. The candidates are all \(n!\) arrangements, finitely many, generated one per iteration (termination measure: the number of arrangements not yet generated, which drops by 1 each iteration). At least one arrangement is sorted (lesson 1, Theorem 10; with distinct keys, Theorem 7), and it passes the check. So the loop reaches a passing candidate and returns it, possibly an earlier passing one.

Notice that the proof never used distinct keys. The algorithm is correct even with ties, and the reason is a small detail: the check asks “is \(b_{i+1} < b_i\)?” (is this pair out of order?), not “is \(b_i < b_{i+1}\)?” (is this pair strictly increasing?).

Small details like that are exactly what goes wrong in real code. So let’s stress the proof with two plausible mistakes and see where it catches each one.

  1. Mistake 1: checking for strict increase. Suppose the check is written as if not b[i] < b[i + 1]: return False, demanding that each item be strictly smaller than the next. With distinct keys that makes no difference. But give it a tie, say [2, 1, 2]. Every sorted arrangement looks like 1, 2, 2, with the two 2s side by side, and there the check asks “is 2 < 2?”, gets “no”, and rejects it. So even the right answer fails the check. No candidate passes, the loop runs out, and the function falls off the end and returns None. Where does the proof catch this? At the step “the sorted arrangement passes the check”: with ties, a sorted arrangement need not be strictly increasing.
  2. Mistake 2: stopping one pair early. Suppose the loop is written as for i in range(len(b) - 2). Then the last neighbour pair is never compared. On [1, 3, 2] the very first candidate is the input itself; the check compares 1 with 3, finds nothing wrong, stops before looking at 3 and 2, and returns [1, 3, 2]. The proof catches this at the step “passes the check, so it is sorted”: lesson 1, Lemma 11 needs every neighbour pair.

And here are the edge cases proof. Each follows from the proof, and each has also been checked by running the code:

  • []: permutations([]) yields one empty tuple, which passes: returns [], 0 comparisons.
  • [x]: returns [x], 0 comparisons.
  • All equal, [5, 5, 5]: the first candidate passes after 2 comparisons.
  • Already sorted: the first candidate passes after \(n - 1\) comparisons.
  • Duplicates, [2, 1, 2]: returns [1, 2, 2] after 3 candidates and 5 comparisons.

05Cost

Now that we know it’s correct, how much does it cost? First we have to decide what to count. The comparison model says comparisons. We’ll also count candidates because, as we’re about to see, each candidate is cheap to check, and it’s the number of candidates that explodes. (Generating each candidate also copies \(n\) element references into a new tuple. Those moves aren’t comparisons, but they are real work.)

The best case is easy. Every run ends with a candidate that passes, and a passing candidate always costs exactly \(n - 1\) comparisons, because every neighbour pair gets checked. On sorted input the very first candidate passes. So \(B(n) = n - 1\) for \(n \ge 1\) proof.

The worst case takes more thought. Make a guess first.

Predict first

How many comparisons does permutation sort make on the reversed input [4, 3, 2, 1]?

Yes, 40. The explanation below shows exactly where that number comes from.
24 is the number of candidates, and here every one of them is examined. But each costs at least one comparison, and some cost two or three, so the total has to be more than 24.
72 = 24 × 3 charges every candidate all 3 comparisons. But the check stops at the first pair that’s out of order, and most candidates fail at the first or second pair.
Split it into two questions: how many candidates get examined, and how many comparisons does each one cost before it fails?

Forty. Let’s see where that number comes from. We’ll get it in four steps, and along the way we’ll find a formula for every \(n\).

Step 1: which candidates get examined? In [4, 3, 2, 1] the sorted arrangement takes positions (3, 2, 1, 0) in that order, and that is the very last tuple in lexicographic order. So all 24 candidates are examined.

Step 2: what does one candidate cost? The check asks its questions in order and stops at the first “yes”. So it asks its \(j\)-th question (comparing positions \(j - 1\) and \(j\), for \(j = 1, \ldots, n-1\)) exactly when all the earlier questions answered “no”. And with distinct keys, “no” to each of the first \(j - 1\) questions means \(b_0 < b_1 < \cdots < b_{j-1}\). So the \(j\)-th question is asked exactly when the first \(j\) entries of the candidate are increasing.

Step 3: add it up over all candidates. Instead of adding candidate by candidate, let’s add question by question: on how many candidates is the \(j\)-th question asked? On those whose first \(j\) entries are increasing. To build such a candidate, choose which \(j\) elements go first, in \(\binom{n}{j}\) ways; they must then appear in increasing order, which leaves 1 way; and the remaining elements can go in any order, in \((n-j)!\) ways. That’s \(\binom{n}{j}(n-j)! = n!/j!\) candidates. Adding over all the questions:

\[ T(n) \;=\; \sum_{j=1}^{n-1} \frac{n!}{j!}. \]
proof

Read it back: the \(j\)-th term counts the candidates that survive long enough to be asked their \(j\)-th question. A quick sanity check: for \(n = 3\) we get \(6/1 + 6/2 = 9\), and for \(n = 4\) we get \(24 + 12 + 4 = 40\), matching the prediction.

Step 4: could some other input be even worse? No. For any input of distinct elements, the candidates are the same \(n!\) arrangements of its values, so Step 3 applies to them unchanged: checking all of them costs \(T(n)\), whatever the input. Every input stops somewhere along that sequence, so it costs at most \(T(n)\), and the reversed input is the one that stops at the very end.

Theorem 2 (exact cost)

With distinct keys, permutation sort makes \(B(n) = n - 1\) comparisons in the best case (sorted input) and \(W(n) = T(n) = \sum_{j=1}^{n-1} n!/j!\) in the worst case (reversed input). Moreover \(T(n) < 2 \cdot n!\).

Proof

The best and worst cases were derived above. For the bound, write \(T(n) = n!\,\bigl(\tfrac{1}{1!} + \tfrac{1}{2!} + \cdots + \tfrac{1}{(n-1)!}\bigr)\). Since \(j! \ge 2^{j-1}\) (each of the factors \(2, \ldots, j\) is at least 2), each term is at most \(1/2^{j-1}\), and the bracket is less than \(1 + \tfrac12 + \tfrac14 + \cdots = 2\).

Read that back, because it’s surprising. Checking costs fewer than two comparisons per candidate, on average over the candidates: most candidates fail at the very first or second neighbour pair. The explosion comes entirely from the number of candidates.

Going deeper · The constant is e − 1

The bracket \(\sum_{j \ge 1} 1/j!\) converges to \(e - 1 \approx 1.71828\), because \(e = \sum_{j \ge 0} 1/j!\). So \(T(n)/n! \to e - 1\) proof sketch; Table 2 shows it agreeing to four decimals by \(n = 8\).

To feel the scale: \(T(20) \approx 4.18 \times 10^{18}\). At a billion comparisons per second (an assumed rate, not a measurement), that’s about 132 years, to sort 20 numbers.

Q2

[2, 3, 4, 1] and [1, 4, 3, 2] each have exactly 3 out-of-order pairs. Permutation sort examines 19 candidates on the first and 6 on the second. Why so different?

  • The cost depends on where the sorted arrangement falls in the generation order, not on how disordered the input is.
    Yes. The search runs through the same fixed list of position tuples every time and stops at the sorted arrangement, so the count is just that arrangement’s place in the list. For [2, 3, 4, 1] it is (3, 0, 1, 2), number 19; for [1, 4, 3, 2] it is (0, 3, 2, 1), number 6.
  • The first input has more disorder.
    Count them: both have exactly 3 out-of-order pairs, (2, 1), (3, 1), (4, 1) in the first and (4, 3), (4, 2), (3, 2) in the second. Equal disorder can’t explain unequal costs, and in fact this algorithm never measures disorder at all.
  • The second input is closer to sorted, so the check passes sooner.
    That would be true of an algorithm that repairs the input bit by bit, but this one doesn’t start from the input’s order. It generates arrangements in a fixed sequence and checks each one from scratch; the input only decides where in that sequence the sorted arrangement appears.
  • Random variation.
    Nothing here is random: permutations always produces the same sequence, and each check gives the same answers every time. Run it twice on the same input and you get exactly the same count.
The algorithm doesn’t improve the input step by step; it runs through a fixed list of candidates. So what decides when it stops?
Write each input’s sorted arrangement as a tuple of positions. In [2, 3, 4, 1] the smallest value sits at position 3, the next at position 0, and so on. Where does each tuple come in lexicographic order?

Permutation sort stops at the first candidate that passes, and that is the sorted arrangement. So the number of candidates it examines is simply the sorted arrangement’s place in the generation order, the lexicographic order of position tuples.

  • [2, 3, 4, 1]: the values 1, 2, 3, 4 sit at positions 3, 0, 1, 2, so the sorted arrangement is the tuple (3, 0, 1, 2). Every tuple that starts with 0, 1 or 2 comes before it, 6 of each, 18 in all, and it is the first tuple that starts with 3: number 19.
  • [1, 4, 3, 2]: the values 1, 2, 3, 4 sit at positions 0, 3, 2, 1, giving (0, 3, 2, 1), the last of the six tuples that start with 0: number 6.

So (a) is the reason. The two inputs have equal disorder, which rules out (b), and (c) assumes the algorithm builds on the input’s order, which it never does. The whole process is deterministic, so (d) is out too.

06What it knows, and what it wastes

The cost is absurd. But why, exactly? Where does all that work go? Not into checking each candidate: that’s fewer than two comparisons per candidate. The trouble is the sheer number of candidates, and that raises a suspicion. There are only \(n(n-1)/2\) different pairs to ask about (6 for four items), yet the algorithm asks dozens or thousands of questions. So it must be asking about the same pairs again and again, and perhaps learning nothing from most of its comparisons. To test that suspicion we need to say precisely what the algorithm knows at each moment. Let’s start with an experiment.

Predict first

Yes, after just 3. The other 4 comparisons tell it nothing new; the explanation below shows why.
7 is when it stops, but stopping and knowing aren’t the same thing. Watch the diagram in Fig. 1: at which comparison does it become a single chain?
Close. After 2 comparisons it knows 2 < 3 and 1 < 3, but not yet how 1 and 2 compare, so two orders are still possible.
Keep track of which pairs have been compared, and what follows from those answers by transitivity. When is every pair settled?

The first three questions are 3 < 2? (no), 1 < 3? (yes), 1 < 2? (yes). After them the algorithm knows 1 < 2 < 3, the whole order. It then examines two more candidates, (3, 2, 1) and (3, 1, 2), that contradict what it already knows, and asks four more questions whose answers it already has.

So what does the algorithm know, exactly? Each comparison hands it one fact: \(x < y\) or \(y < x\). And facts combine: from \(1 < 2\) and \(2 < 3\) it may conclude \(1 < 3\) without asking, by transitivity. That’s all it can ever learn, because in the comparison model the elements themselves are invisible (lesson 3, §03).

Lesson 1 already gave us exactly the right object to hold that kind of information. A set of facts “\(x\) before \(y\)”, together with everything transitivity adds to them, is a strict partial order (no cycles can arise, because all the facts are true of one real input), and lesson 1 drew such things as Hasse diagrams. The arrangements consistent with a partial order are its linear extensions, and there are \(e(P)\) of them. So here’s a natural guess: what the algorithm knows is a partial order, and the inputs it can’t yet rule out are its linear extensions. In fact, Fig. 1 has been drawing exactly that partial order under the stepper all along. The guess is right:

Theorem 3 (knowledge is a partial order)

Let \(O\) be the outcomes of the comparisons made so far on some input with distinct keys, and \(P\) the strict partial order they generate (their transitive closure). Then:

(a) the inputs (rank patterns) that would have produced exactly these outcomes are those whose sorted order is a linear extension of \(P\); there are \(e(P)\) of them;

(b) if \(x\) and \(y\) are unrelated in \(P\), some input consistent with \(O\) has \(x < y\) and another has \(y < x\).

Proof

(a) A rank pattern is a strict total order on the elements. It produces the observed outcomes exactly when it agrees with every outcome in \(O\). A total order is transitive, so agreeing with \(O\) is the same as agreeing with everything \(O\) implies, that is, with \(P\); and a total order agreeing with \(P\) is precisely one whose sorted arrangement is a linear extension of \(P\).

(b) Adding \(x \prec y\) to \(P\) creates no cycle, because a cycle through the new pair would need \(y \prec x\) in \(P\) already. By lesson 1, Corollary 6, some linear extension puts \(x\) before \(y\). Symmetrically, some puts \(y\) before \(x\). By (a), both are consistent inputs.

Let’s read it back. At any moment, the algorithm’s knowledge is a partial order \(P\): the facts it has observed plus their consequences, and nothing more. The number of inputs it still can’t rule out is \(e(P)\). It can be certain of the sorted order exactly when \(e(P) = 1\), that is, when \(P\) has become a total order. And a comparison whose answer is already in \(P\), because that pair was asked before or because transitivity implies it, cannot change \(P\) at all: it teaches nothing.

This way of looking at an algorithm is the knowledge lens, and it will be the main lens of this course. For every algorithm we meet, we’ll ask: what partial order does it hold, what shape is it, and does each comparison change it?

Through this lens we can now say exactly how permutation sort wastes its effort. There are two ways:

  • It asks questions it can already answer. On the reversed input of size 4 it makes 40 comparisons, but only \(\binom{4}{2} = 6\) pairs exist: at least 34 of its comparisons ask about a pair already asked. It has the full order after comparison 24 and keeps going for 16 more.
  • It tests candidates its knowledge has already ruled out. On [2, 3, 1] it knew the answer after 3 comparisons and still checked two candidates that contradicted it.

In short, the algorithm treats each candidate as a fresh question and forgets everything it learned in between.

So the related pairs are exactly those three.

  • (a) \(a\) vs \(b\): no chain. Consistent orders include abcd (\(a\) first) and bacd (\(b\) first).
  • (b) \(c\) vs \(d\): no chain. abcd has \(c\) first, abdc has \(d\) first.
  • (d) \(a\) vs \(d\): no chain. abcd has \(a\) first, bdac has \(d\) first.
  • (c) \(b\) vs \(c\): \(b < c\) is a known fact. All five orders still possible put \(b\) before \(c\), so the answer removes none of them.

Only (c) teaches nothing. Pairs that merely appear in the facts, like \(a\) and \(d\), aren’t enough: what settles a pair is an actual chain between them.

Q5

In the situation of Q4, how many orderings of the four elements are still possible?

Yes, \(e(P) = 5\): abcd, abdc, bacd, badc and bdac. It’s lesson 1’s tasks poset again, and these are the same five orders lesson 1 found.
24 is every ordering of four elements, as if nothing were known. But each known fact rules orderings out: by Theorem 3(a), only the linear extensions of the known partial order remain.
3 is the number of pairs still undecided (\(a\) and \(b\), \(c\) and \(d\), \(a\) and \(d\)), not the number of orders. Each of them can still go either way, and different combinations give different orders, so count the orders directly: which element can go first?
Count the linear extensions of a ≺ c, b ≺ c, b ≺ d (lesson 1, Fig. 3). Ask which elements can go first, then which can go next, and so on.
By Theorem 3(a), the orderings still possible are the linear extensions of what’s known. Lesson 1’s question counts them: which elements could go first?
Only \(a\) and \(b\) have nothing known below them, so one of them goes first. If \(a\) goes first, the next must be \(b\), since \(c\) and \(d\) both have \(b\) below them. If \(b\) goes first, what could come next?

Theorem 3(a) says the orderings still possible are exactly the linear extensions of a ≺ c, b ≺ c, b ≺ d. Let’s count them with lesson 1’s question: which element can go first? An element can go first when nothing is known to be smaller than it, and here that’s \(a\) or \(b\) (\(c\) has \(a\) and \(b\) below it, and \(d\) has \(b\)).

  • \(a\) first. Next only \(b\) can go, because \(c\) and \(d\) both need \(b\) before them. Then \(c\) and \(d\) are both free, in either order: abcd, abdc. That’s 2.
  • \(b\) first. Next \(a\) or \(d\) can go (\(c\) still needs \(a\)). After b, a: \(c\) and \(d\) in either order, giving bacd and badc. After b, d: only \(a\) can go, then \(c\), giving bdac. That’s 3.

Total: 2 + 3 = 5. Answering 24 ignores what’s known, and answering 3 counts the undecided pairs rather than the orders they lead to.

07Remember what you learn

The waste points straight at a fix: never ask a question whose answer you already know. Let’s follow that advice in its bluntest form, and ask about every pair exactly once. With distinct keys, every pair is related one way or the other, so once every pair has been asked, the algorithm knows the whole strict total order: \(e(P) = 1\). All that’s left is bookkeeping, turning that knowledge into the one sorted arrangement.

How do we turn “all pairs known” into an arrangement? Look at the answer we’re aiming for. By lesson 1, Theorem 7, the sorted arrangement is \(x_0 \prec x_1 \prec \cdots \prec x_{n-1}\). The element at position \(r\) has exactly \(r\) elements before it, all smaller, and all the others after it, all larger. So an element’s position is simply the number of elements smaller than it. That number is its rank, and we can compute it by letting every pair award a point to its larger element.

Why the else? With distinct keys, if \(a_j < a_i\) is false then \(a_i < a_j\), so each pair awards exactly one point, to its larger element.

Invariant (after the double loop)

rank[i] equals the number of elements \(a_j\) with \(a_j < a_i\).

Theorem 4 (comparison counting)

With distinct keys, rank_sort returns the sorted permutation of a and makes exactly \(n(n-1)/2\) comparisons on every input.

Proof

Each pair \(\{i, j\}\) is compared exactly once and gives one point to its larger element, which proves the invariant. If \(x < y\), everything smaller than \(x\) is also smaller than \(y\), and so is \(x\) itself; so rank(\(x\)) < rank(\(y\)). Hence the \(n\) ranks are distinct numbers in \(\{0, \ldots, n-1\}\), so they are exactly \(0, \ldots, n-1\): every slot of b is written exactly once, which makes b a permutation of a. And smaller elements get smaller positions, so b is sorted. The comparison count is the number of pairs, \(\binom{n}{2}\), whatever the input.

Knuth calls this comparison counting. Now compare the two algorithms. For \(n = 10\), permutation sort’s worst case is 6 235 300 comparisons; comparison counting always uses 45. That entire gap is the value of remembering what you’ve learned.

Theorem 4 assumed distinct keys, though. What happens with ties? Make a prediction.

Predict first

What does rank_sort([5, 5, 5]) return?

  • [5, 5, 5]
    Yes, [5, 5, 5], and correctly so. The explanation below shows why the ties do no harm.
  • [5, None, None]
    That’s what the tempting “more careful” version returns, the one that gives no point on a tie. Listing 2’s else behaves differently; the explanation below shows how.
  • It raises an IndexError.
    A reasonable worry, but every rank stays between 0 and \(n - 1\), so no index goes out of range. The explanation below shows what happens instead.

It returns [5, 5, 5], correctly. Here’s why. For a tied pair \(i < j\), a[j] < a[i] is false, so the else hands the point to a[j], the later element. In effect, ties are broken by position: the code is really ranking by the pair (key, position), which is a strict total order by lesson 2, Theorem 2. So the ranks are still all different, the proof goes through unchanged, and as a bonus tied elements keep their input order (the property lesson 7 calls stability).

Now look at a tempting “more careful” version, which gives no point to either element on a tie:

if a[j] < a[i]:
    rank[i] += 1
elif a[i] < a[j]:
    rank[j] += 1

On [5, 5, 5] all the ranks stay 0, every element is written into b[0], and the result is [5, None, None], which isn’t even a permutation. The proof fails at “the ranks are distinct”. So the else was never a shortcut: it was the tie-breaking rule.

So, are all \(n(n-1)/2\) questions really needed? Comparison counting never uses transitivity: it asks every pair, even when the answer follows from earlier ones. Look at a sorted input of 4 elements. The three neighbour questions \(a_0 < a_1\), \(a_1 < a_2\) and \(a_2 < a_3\) already prove the whole order (lesson 1, Lemma 8), and the other three answers are mere consequences. So how few questions could possibly be enough? That’s where lesson 5 begins.

In practice neither is how you sort: sorted(a) is. E3

Why is the reversed input a worst case for permutation sort?

  • Its sorted arrangement is the last one generated, and the total cost of checking all \(n!\) candidates is the same \(T(n)\) for every input.
    Yes, and both halves matter. The first says the reversed input makes the search check every candidate. The second says checking every candidate costs the same \(T(n)\) for any input, and no input can cost more than checking everything, so the reversed input reaches the maximum.
  • It has the most out-of-order pairs.
    It does have the most, but that isn’t why it’s worst here: this algorithm never measures disorder. Q2 showed two inputs with equal disorder and very different costs. What matters is where the sorted arrangement sits in the generation order.
  • Every candidate fails at the last neighbour pair.
    Most candidates fail at the very first or second pair, not the last; that’s exactly why \(T(n) < 2 \cdot n!\). For \(n = 4\), only 4 of the 24 candidates even reach the third pair.
  • Because \(n!\) is the largest factorial.
    \(n!\) is the number of candidates for every input of size \(n\), so it can’t single out the reversed one. What changes from input to input is how many of those candidates get examined before the search stops.
Calling an input a worst case takes two facts: it costs a lot, and nothing costs more. Which option supplies both?
Where in the generation order does the reversed input’s sorted arrangement appear? And does the cost of checking all \(n!\) candidates depend on the input?

To show that an input is a worst case we need two facts: what it costs, and that no input costs more.

  1. The reversed input checks every candidate. Its sorted arrangement takes positions \((n-1, \ldots, 1, 0)\), the very last tuple in lexicographic order, so nothing stops the search before the end.
  2. Nothing can cost more. For any input of distinct elements, the candidates are the \(n!\) arrangements of its values, and §05 showed that checking all of them costs \(T(n) = \sum_{j=1}^{n-1} n!/j!\) whatever the input. Every input stops somewhere along that sequence, so it costs at most \(T(n)\).

That’s option (a). Option (b) states something true about the reversed input but gives the wrong reason: Q2’s inputs [2, 3, 4, 1] and [1, 4, 3, 2] have equal disorder, yet they need 19 and 6 candidates. Option (c) is false: the \(j\)-th question is asked on only \(n!/j!\) candidates, so most candidates fail at the first or second pair. Option (d) confuses the number of candidates, which is \(n!\) for every input, with the number examined.

  • Lesson 1, Lemma 8.

  • Lesson 1, Theorem 5.

Ledger

Established

  • Permutation sort is correct for any strict weak ordering proof §04
  • Its best case is \(n - 1\) comparisons (sorted input) and its worst case is \(T(n) = \sum_{j=1}^{n-1} n!/j! < 2 \cdot n!\) (reversed input) proof; \(T(n)/n! \to e - 1\) proof sketch §05
  • Its cost depends on where the answer sits in the generation order, not on how disordered the input is proof, by example §05
  • Knowledge theorem: after any comparisons, the algorithm’s knowledge is a partial order \(P\); the inputs still possible are the \(e(P)\) linear extensions; unrelated pairs can still go either way proof §06
  • Comparison counting sorts with exactly \(n(n-1)/2\) comparisons on every input, correctly with ties thanks to its tie-breaking by position proof §07

Assumptions in force

  • Comparison model; cost = comparisons, worst case; A1 (distinct keys) for the cost results; the correctness results allow ties.

Lenses in use

  • Knowledge (introduced): what the algorithm knows is a partial order; \(e(P)\) counts what it still cannot rule out; comparisons whose answers are known or implied teach nothing. So far it has explained why permutation sort wastes almost all of its work.

Reasoning tools acquired

  • Correctness as three claims (permutation, sorted, returns) plus a decreasing termination measure.
  • Stress-testing a proof by finding where a buggy variant breaks it.
  • Exact counting by asking “on how many candidates is comparison \(j\) made?”.
  • Bounding a sum by a geometric series.
  • The knowledge view: partial order, linear extensions, wasted comparisons.
