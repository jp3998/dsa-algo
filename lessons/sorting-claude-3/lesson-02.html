Lesson 2

What must a comparison promise?

Stage 0 · Foundations

Where we are

Lesson 1 found what “in order” means. A request is a rule about pairs, a relation, and a correct answer is an arrangement with no pair out of order. A relation has such an arrangement exactly when it has no cycle. It has exactly one when it is a strict total order. When it is a strict weak ordering, its answers are its tiers in order, and checking neighbours is enough to recognise one.

All of that assumed we could see the whole relation, like the lists of lesson 1’s Table 1. A program cannot. A sorting program is handed the items and a way to ask about two of them at a time, “is x before y?”, and it must work from the answers alone. In Python that question is the < operator. This lesson asks what the code behind < must satisfy, how Python lets us supply it, what goes wrong in practice when it fails, and how to prove that an unusual comparison is safe.

  • Depends on: Lesson 1 §06: strict weak orderings and tiers; Lesson 1 §05: the neighbour test.

Prerequisite check

Q1

Under "noticeably smaller" (\(x \prec y\) iff \(y - x > 1\)), which arrangement passes the neighbour test but is not sorted?

  • 2.2, 1.5, 1.0
    Each neighbour pair differs by less than 1, so no neighbour pair is out of order; but 1.0 ≺ 2.2 and 1.0 comes last.
  • 1.0, 1.5, 2.2
    This one is sorted: nothing later is required before anything earlier.
  • 2.2, 1.0, 1.5
    The neighbour test catches this: 2.2 and 1.0 are neighbours and 1.0 ≺ 2.2.
  • 1.5, 1.0, 2.2
    This is sorted: the only required pair is 1.0 ≺ 2.2, and 1.0 comes first.

Q2

In a strict weak ordering, what is a tier?

  • A class of elements that are pairwise unrelated; the tiers themselves are totally ordered.
    That is Lemma 9 of lesson 1. Ties live inside a tier; every pair from different tiers is related.
  • An element with nothing below it.
    That is a minimal element (lesson 1 §04). A tier is a whole class of mutually unrelated elements.
  • A chain \(x_1 \prec x_2 \prec \cdots\).
    A chain's elements are all related to each other. A tier's elements are related to none of each other.
  • The set of all elements below a given \(x\).
    That set can contain related elements. A tier contains only mutually unrelated ones.

01The only question Python asks

Python's sorting functions, sorted(xs) and xs.sort(), rearrange elements using one question: a < b. Python's documentation states this guarantee: the sort routines use only < when comparing two objects. So a class that defines nothing but __lt__ can be sorted:

In lesson 1’s terms, < is the relation \(\prec\), handed to the sort not as a list of pairs but as a function it may call on any pair. The sort calls it on some pairs, not on all of them: asking every pair would cost \(n(n-1)/2\) questions, far more than a good sort spends (lesson 3 counts what Python’s sort actually spends). For the pairs it never asks about, the sort relies on the answers it did get chaining together, the way lesson 1’s neighbour test relies on transitivity to vouch for pairs that are not neighbours.

Lesson 1 also showed when such chaining is safe. For a strict weak ordering, “no neighbour pair out of order” really does mean “no pair out of order” (lesson 1, Lemma 11). For a mere partial order it does not: the tasks of request (C) fooled the neighbour test with d, a, b, c. So we should expect a sort’s output to mean something only when the < it is given is a strict weak ordering intuition. (Exactly how a particular sort can be misled depends on which pairs it asks about; §05 shows what Python’s sort does in practice.) And nothing checks this: Python trusts your < and never tests it.

So the question becomes concrete: when we hand Python a way to compare, how can we be sure it is a strict weak ordering? Python accepts two kinds of comparison. A key function says what to compare; a comparison function says how two elements compare. We take them in turn, starting with keys, because keys turn out to be safe by construction.

02Keys always give a well-behaved order

Real data are records: people, tasks, intervals. We rarely sort them by "the record"; we sort by some property of it: age, deadline, length. Python's key= parameter does this: sorted(people, key=age) computes age(p) once for each element and compares those values with <.

Notice what is compared. Sorting people by age never compares two people; it compares their ages, which are numbers. The order on people is borrowed from the order on numbers. Any such borrowed order deserves a name.

Definition (relation induced by a key)

Let \(f\) map each element of \(X\) to a set \(K\) of keys that carries a strict total order \(<\). The relation induced by \(f\) is \(x \prec_f y\) iff \(f(x) < f(y)\).

Request (B) of lesson 1 is a borrowed order of exactly this kind, with the key “age”: Dee ≺ Ben because 22 < 25, and Ana and Cy tie because their keys are equal, 30 = 30.

Two questions about borrowed orders. Is a borrowed order always a strict weak ordering, the kind of rule lesson 1 showed sorting needs? And does every strict weak ordering arise this way, or are there well-behaved rules that no key can produce? Theorem 1 settles both: a borrowed order is always a strict weak ordering, and every strict weak ordering is a borrowed order.

Theorem 1 (keys give exactly the strict weak orderings)

(a) Every relation induced by a key is a strict weak ordering; its tiers are the sets of elements with equal keys. (b) Conversely, every strict weak ordering on a finite set is induced by some key.

Proof

(a) Irreflexive: \(f(x) < f(x)\) never holds. Transitive: \(f(x) < f(y) < f(z)\) gives \(f(x) < f(z)\). Ties: since \(<\) is total on \(K\), "neither \(f(x) < f(y)\) nor \(f(y) < f(x)\)" means exactly \(f(x) = f(y)\), and equality is transitive. So \(\sim\) is transitive and its classes are the sets of equal keys.

(b) By lesson 1, Lemma 9, the tiers line up as \(T_1, T_2, \ldots, T_k\), and \(x \prec y\) holds exactly when \(x\)'s tier comes before \(y\)'s. So the key \(f(x) = i\) for \(x \in T_i\) induces \(\prec\).

Read it back. Part (a) is the reason key= is safe: whatever function you write, the induced order is a strict weak ordering, provided the key values themselves are totally ordered by <. That proviso is exactly where things go wrong in §05. Part (b) says nothing is lost by thinking of every well-behaved comparison as "compare some key". We will use (b) in §06 to prove that a strange-looking comparator is well behaved, by finding its hidden key.

Ties keep their input order: sorted(["pear", "fig", "kiwi", "plum", "apple"], key=len) returns ['fig', 'pear', 'kiwi', 'plum', 'apple'], with the three 4-letter words in their original order. Python guarantees this property, called stability; lesson 7 shows why anyone needs it.

03Several keys: lexicographic order

Often one property does not decide. Two people have the same age, and we want the tie broken by name. We need an order on pairs (age, name) that compares ages first and looks at names only on a tie.

A dictionary already works this way. The first letter decides; only when the first letters agree does the second letter matter, and so on. The order is named after the dictionary: lexicographic, from “lexicon”. For pairs it reads:

Definition (lexicographic order on pairs)

Given strict total orders on the first and on the second coordinates, \((p, q) <_{\text{lex}} (p', q')\) iff \(p < p'\), or \(p = p'\) and \(q < q'\).

If the pair (age, name) could be treated as one single key, Theorem 1 would make the borrowed order safe at once. Theorem 1 asks one thing of its keys: that they are compared by a strict total order. So that is what we must check for pairs compared lexicographically.

Theorem 2 (lexicographic order is total)

If both coordinate orders are strict total orders, \(<_{\text{lex}}\) is a strict total order on pairs.

Proof

Irreflexive: \((p,q) <_{\text{lex}} (p,q)\) would need \(p < p\) or \(q < q\).

Transitive: let \((p_1,q_1) <_{\text{lex}} (p_2,q_2) <_{\text{lex}} (p_3,q_3)\). The first step gives \(p_1 \le p_2\) and the second \(p_2 \le p_3\). If either step was decided by the first coordinate, then \(p_1 < p_3\) and we are done. Otherwise both steps were ties on the first coordinate, \(p_1 = p_2 = p_3\), and \(q_1 < q_2 < q_3\) gives \(q_1 < q_3\).

Total: two different pairs differ in the first coordinate, which decides, or agree there and differ in the second, which decides.

The same argument extends to triples and longer sequences by induction. Python compares tuples (and lists and strings) this way: find the first position where they differ, and compare there; if one is a prefix of the other, the shorter is smaller. So key=lambda r: (r.age, r.name) is a key into a totally ordered set, and Theorem 1 makes the induced order a strict weak ordering whose tiers are records with equal age and name.

Descending order on a numeric field is a negated key: key=lambda t: (-t[0], t[1]) sorts by score descending, then name ascending. On [(90, "Lee"), (85, "Ana"), (90, "Bo"), (70, "Cy")] it gives [(90, 'Bo'), (90, 'Lee'), (85, 'Ana'), (70, 'Cy')].

Common question · How do I sort descending by a string?

You cannot negate a string. reverse=True reverses the whole order, so it makes every level descending: with key=lambda t: (t[0], t[1]) and reverse=True the example above gives [(90, 'Lee'), (90, 'Bo'), (85, 'Ana'), (70, 'Cy')]: names descending too. For mixed directions on strings, either sort twice using stability (lesson 7 explains why that works), or write a comparison function (§04).

Note

Tuple keys compare later components only on ties, and then those components must support <. A heap or list of (priority, record) tuples works until two priorities are equal; then Python compares the records. If they are dictionaries, that raises TypeError: '<' not supported between instances of 'dict' and 'dict'. Exercise E2 below is this bug.

Checkpoint 1

Q1

You want words sorted by length, and words of equal length alphabetically. Which call does it?

  • sorted(words, key=len)
    Ties keep their input order (stability), not alphabetical order. ['pear', 'fig', 'kiwi', 'plum', 'apple'] gives ['fig', 'pear', 'kiwi', 'plum', 'apple']: pear before kiwi.
  • sorted(words, key=lambda w: (len(w), w))
    Lexicographic: length decides, and the word itself decides only among words of equal length. Result: ['fig', 'kiwi', 'pear', 'plum', 'apple'].
  • sorted(words, key=lambda w: (w, len(w)))
    The first coordinate decides whenever it differs, and different words always differ. Length is never consulted; this is plain alphabetical order.
  • sorted(words, key=lambda w: len(w) + w)
    len(w) + w adds an int to a str and raises TypeError. Combining criteria is what tuples are for.

Q2

Records are (score, name). You want the highest score first and, among equal scores, names A to Z. Which works?

  • key=lambda t: (-t[0], t[1])
    Negating the score reverses only that level.
  • key=lambda t: (t[0], t[1]), reverse=True
    reverse=True reverses the whole lexicographic order, so names among equal scores come out Z to A.
  • key=lambda t: (-t[0], -t[1])
    -t[1] negates a string and raises TypeError. And the name should not be reversed anyway.
  • key=lambda t: t[0], reverse=True
    Equal scores keep their input order, not alphabetical order.

04Comparators and their contract

Keys are safe, but some rules are easier to state about a pair than about a single element. All of lesson 1’s rules were of that kind, and here is a Python example, which §06 takes up. To arrange numbers so that writing them side by side gives the largest possible number, the natural rule compares two numbers \(a\) and \(b\) by trying both concatenations, \(ab\) and \(ba\). No key is in sight.

For rules like this, Python accepts a comparison function through functools.cmp_to_key(cmp). The function cmp(a, b) returns a negative number if a should come first, a positive number if b should, and 0 for a tie. cmp_to_key wraps each element in an object whose < calls cmp(a, b) < 0. Since the sort only ever asks <, the relation the sort sees is

\[ a \prec b \iff \texttt{cmp}(a, b) < 0. \]

By §01, this relation must be a strict weak ordering. One further condition is plain hygiene: swapping the arguments should flip the sign, so that a positive answer means what it says. Together these form the contract that every comparison function must honour.

Definition (comparator contract)

A comparison function is valid if the relation \(a \prec b \iff \texttt{cmp}(a,b) < 0\) is a strict weak ordering, and its signs agree: \(\texttt{cmp}(a,b) < 0\) exactly when \(\texttt{cmp}(b,a) > 0\).

Unlike a key, a comparison function can break the contract silently. How would you find out? On a finite sample of values the contract can be checked by brute force: test irreflexivity on every element, transitivity on every triple, and transitivity of ties on every triple. A counterexample is a triple that proves the comparison broken. Passing the check on a sample is evidence about other values, not proof. Listing 2 is the check, and Fig. 1 runs it on seven comparisons.

05What happens when the promise breaks

Four of the seven comparisons in Fig. 1 fail the check, and each is one that people actually write: a tolerance for floats that are “close enough”, plain < on floats that include NaN, a cyclic “beats”, and < on sets. What does Python do with them? Start with NaN.

Predict first

nan = float("nan"). What does sorted([3.0, nan, 1.0, 2.0]) return?

  • [1.0, 2.0, 3.0, nan]
    A natural guess: "NaN goes last". See below.
  • [nan, 1.0, 2.0, 3.0]
    Python has no rule putting NaN first. See below.
  • [3.0, nan, 1.0, 2.0], unchanged
    Yes, surprisingly. See below.
  • It raises an error.
    Python raises no error. See below.

CPython returns the list unchanged: [3.0, nan, 1.0, 2.0] empirical. Every comparison involving NaN is false (nan < x and x < nan are both False), so the sort sees NaN as tied with every number. Ties with NaN chain any two numbers together: 1.0 ∼ NaN ∼ 3.0, yet 1.0 < 3.0. That is a broken "ties are transitive" axiom, and lesson 1, §06 showed that the neighbour test then lies.

The output depends on where NaN starts empirical:

The same happens with max and min, which use comparisons too: max([nan, 1.0, 2.0]) is nan, but max([1.0, nan, 2.0]) is 2.0.

The other broken comparisons behave the same way: no error, and an answer that depends on the starting order.

In every run the output was a rearrangement of the input: nothing lost or duplicated empirical. Python's documentation makes no promise about which rearrangement you get when the comparison is inconsistent, so do not rely on any of these outputs.

Why does a sort fall into this? It is the failure §01 warned about intuition. A sort never asks about every pair; it relies on the answers it got chaining together. When ties do not chain, a run of “ties” can connect two elements that are in fact ordered, as 3.0 ∼ 2.4 ∼ 1.8 ∼ 1.2 ∼ 0.6 connects 3.0 to 0.6 under the tolerance comparison, and the sort never asks about the pair that would expose it. The algorithm is not at fault; its precondition was violated. (Some languages detect some violations: Java’s library sort sometimes throws “Comparison method violates its general contract!”. Python does not.)

The repairs follow from Theorem 1: turn the broken comparison into a key into a totally ordered set, and the result is a strict weak ordering by construction.

The NaN key puts every number in the tier (False, value) and every NaN in the tier (True, nan), which comes last. Within the NaN tier all elements tie, and that is consistent. The grid key is a genuine key, so it is a strict weak ordering, but it changes the meaning: 0.49 and 0.51 land in different buckets though they are close, while 0.51 and 1.49 land in the same one. That trade-off is unavoidable: "approximately equal" is not transitive, so no strict weak ordering can capture it exactly.

06A comparison whose transitivity is not obvious

Now the rule promised in §04. Given non-negative integers, arrange them so that writing them one after another forms the largest possible number. For [3, 30, 34, 5, 9] the answer is 9534330. Before reaching for a pairwise rule, try the obvious key.

Predict first

Does sorting the numbers as strings in descending order give the answer?

  • Yes.
    Try it below.
  • No.
    Right; here is the failure.

Descending string order gives 9, 5, 34, 30, 3, that is 9534303, smaller than 9534330. The culprit is 3 versus 30. As strings, "30" > "3" (a longer string with the same prefix is larger), but \(330 > 303\): 3 should come first.

So the order of the strings themselves is the wrong key. The right comparison for a pair is the one the problem actually asks about: put \(a\) before \(b\) when writing \(a\) then \(b\) gives the larger number. Write \(ab\) for the number formed by \(a\) followed by \(b\).

\[ a \prec b \iff ab > ba \]

For example \(3 \prec 30\) because \(330 > 303\). In code this is a + b > b + a on the decimal strings. (The two strings have the same length, and for digit strings of the same length, string order and numeric order agree.)

Before sorting by this rule we must know it honours the contract of §04. Irreflexive, yes: \(aa > aa\) is false. Transitive? Suppose \(ab > ba\) and \(bc > cb\). Must \(ac > ca\)? Each comparison glues a different pair of numbers together in two different ways, and there is no obvious quantity that grows along the chain. Pushing digit strings around directly goes nowhere.

Theorem 1(b) suggests a different route. If the rule is a strict weak ordering, some key produces it, and if we can find that key, Theorem 1(a) proves the rule safe at once. So look for the key: a number attached to each \(a\) that grows exactly when \(a\) should come earlier.

Theorem 3 (the hidden key)

Let \(|a|\) be the number of decimal digits of \(a\) and \(f(a) = \dfrac{a}{10^{|a|} - 1}\). Then \(ab > ba \iff f(a) > f(b)\). Hence \(\prec\) is induced by a key (sort by \(f\), largest first) and is a strict weak ordering.

Proof

As numbers, \(ab = a \cdot 10^{|b|} + b\) and \(ba = b \cdot 10^{|a|} + a\). So

\[ ab > ba \iff a\,10^{|b|} + b > b\,10^{|a|} + a \iff a\,(10^{|b|} - 1) > b\,(10^{|a|} - 1). \]

Both \(10^{|a|} - 1\) and \(10^{|b|} - 1\) are positive, so dividing by their product keeps the direction: \(ab > ba \iff f(a) > f(b)\). Ordering by \(f\) in decreasing order is ordering by the key \(-f(a)\), so Theorem 1(a) applies.

Read it back. \(f(a)\) is the value of the infinitely repeated decimal \(0.aaa\ldots\): \(f(3) = 0.333\ldots = 1/3\), \(f(30) = 0.3030\ldots = 30/99\), \(f(34) = 0.3434\ldots = 34/99\). The comparison "which concatenation is larger" is secretly "which infinite repetition is larger". Sanity check on the example: \(f(9) = 1\), \(f(5) = 0.555\ldots\), \(f(34) = 0.3434\ldots\), \(f(3) = 0.333\ldots\), \(f(30) = 0.3030\ldots\), giving 9, 5, 34, 3, 30, which is 9534330. Ties are real: \(f(12) = 12/99 = 4/33 = 1212/9999 = f(1212)\), and indeed \(12|1212 = 121212 = 1212|12\).

Knowing the rule is safe tells us that sorting by it is meaningful. It does not yet tell us that the sorted arrangement forms the largest number; that is a separate claim, and it needs its own argument.

Theorem 4 (sorting gives the maximum)

Every arrangement sorted by \(\prec\) forms the largest possible number.

Proof

Take an arrangement that is not sorted. Since \(\prec\) is a strict weak ordering, lesson 1, Lemma 11 gives a neighbour pair out of order: \(b\) immediately followed by \(a\) with \(a \prec b\), that is \(ab > ba\). Swap them. The digits before and after the pair do not move, and the block \(ba\) in the middle becomes \(ab\): the same length, and larger. So the whole number grows: a non-sorted arrangement is never the largest.

Among the finitely many arrangements one is the largest; by what we just showed it is sorted. Finally, all sorted arrangements give the same number. They differ only in the order inside tiers (lesson 1, Theorem 10), elements of a tier sit next to each other, and for two elements \(a, b\) of the same tier \(ab = ba\), so swapping neighbours inside a tier never changes the digits. Any order of a tier can be reached by such swaps. So every sorted arrangement gives the maximum.

This is an exchange argument: show that any solution breaking the rule can be strictly improved by exchanging two neighbouring elements. It is the standard way to prove that a greedy "sort by the right key, then take them in order" strategy is optimal, and it returns in lesson 21.

The proof also hands us a key directly, so cmp_to_key is not needed: sorted(strs, key=lambda s: Fraction(int(s), 10 ** len(s) - 1), reverse=True) with from fractions import Fraction. Use Fraction, not floats: a float keeps only about 16 significant digits, so for long numbers two different keys can round to the same float.

07In Python: summary of the contract

  • sorted and list.sort ask only <. The result is meaningful when that < is a strict weak ordering; otherwise you get some rearrangement, with no error.
  • A key= function always yields a strict weak ordering, provided the key values are totally ordered: plain numbers without NaN, strings, and tuples of such values.
  • Tuples break ties lexicographically. Later components are compared only on ties, and then they must support <.
  • cmp_to_key(cmp) is the tool for pairwise rules. The contract: \(\texttt{cmp}(a,b) < 0\) must be a strict weak ordering, with consistent signs. Check a comparator on a sample with check_strict_weak (Listing 2) when in doubt.
  • To prove a pairwise rule is well behaved, look for a key (Theorem 1(b)). To prove sorting by it is optimal for some goal, use an exchange argument.

E3

  • Ties are not transitive: {1} ties {3} and {3} ties {1, 2}, yet {1} < {1, 2}.
    For sets, < means proper subset: a strict partial order, but not a strict weak ordering. Sorting sets by subset order is a lesson 35 problem (one valid order of a partial order), and sorted does not solve it.
  • < on sets is not transitive.
    Proper subset is transitive: \(A \subsetneq B \subsetneq C\) gives \(A \subsetneq C\). The failing axiom is the one about ties.
  • < on sets is not irreflexive.
    No set is a proper subset of itself.
  • Nothing is wrong; the output is sorted.
    {1} ⊂ {1, 2}, so {1} must come before {1, 2}, and it comes after.

Ledger

Established

  • Python's sort asks only <; the result is meaningful when < is a strict weak ordering (documented guarantee + lesson 1). §01
  • The relations induced by keys are exactly the strict weak orderings; tiers are the sets of equal keys. proof §02
  • Lexicographic order of strict total orders is a strict total order, so tuple keys are safe. proof §03
  • A comparator for cmp_to_key must make \(\texttt{cmp}(a,b) < 0\) a strict weak ordering (the contract). §04
  • When the contract is broken (tolerance, NaN, cycles, subset order), CPython 3.12 raises no error and returns some rearrangement that depends on the starting order. empirical §05
  • The concatenation rule is induced by the key \(a/(10^{|a|}-1)\) proof; sorting by it gives the largest number proof (exchange argument). §06

Assumptions in force

  • From now on every comparison is assumed to be a strict weak ordering (the precondition of every sort).

  • None yet.

Reasoning tools acquired

  • Proving a pairwise rule is well behaved by finding a hidden key.
  • Checking a comparator on a finite sample; a counterexample triple refutes it.
  • Exchange arguments: any solution breaking the rule can be strictly improved by swapping two neighbours.
